`[2026-08-09 Sun 14:22]` Mechanism verified against the installed companion (`node_modules/jupyterlab_colourful_tab_extension/lib/index.js`): `api.setColour` calls `releaseMenuColour(widget.id)` on any truthy colour, deleting the `terminal:<name>` entry from `jupyterlab-colourful-tab-colours`; `refreshAllTabColours` repaints a stored menu colour only onto a tab carrying no colour class. Reviewed against that, not the comments.

## Verdict
VERDICT: DO-NOT-SHIP (10 findings) - making the override win for `native` closes the only door back out of it, and the destroy-before-persist guard covers one of the three ways the user's choice can be lost.

## Findings

- **[CRITICAL] The override cannot be released from the UI, so a hand-coloured Claude tab kills `/color` for that conversation permanently.** Right-click → Clear (`index.js`, `colourful-tab:clear`) deletes the localStorage entry and strips the classes. On the next `reconcileColours` pass (≤30 s, `terminals.ts:296`), `userSet` is null, nothing is written, and `effectiveColour(…, this._colours.get(sessionId), native)` at `terminals.ts:334-342` repaints the stored override. Nothing in the frontend ever calls `ColourStore.set(id, null)` - grep of `src/` shows only the write-back at `terminals.ts:317`, `inherit` at `panel.ts:934`, and `forget()` on deletion (`panel.ts:674, 1069`). The user perceives "Clear does nothing, the colour flickers back", and `/color` is silently dead for that conversation forever. The ui-test that claims this works (`ui-tests/tests/colour-override.spec.ts:76`) drives `page.request.post` directly and never touches a tab, so it passes on a story no user can perform - and acc-crit line 244 ("Releasing the override hands the conversation back to its default") is marked `[x]` on that evidence. Fix: make the absence of a menu entry on a tab this pass previously coloured mean release - remember per widget the colour last applied from the store, and when `readUserSetTabColour` returns null while the tab carries no colour class, `await this._colours.set(sessionId, null)` before painting.

- **[MAJOR] A failed write-back destroys the colour it failed to save.** `ColourStore.set` (`colour.ts:174-186`) swallows the POST rejection and keeps only the in-memory cache; `reconcileColours` then falls straight through to `_applyColour` (`terminals.ts:334`), whose truthy colour makes the companion call `releaseMenuColour` and delete the localStorage entry. Server 5xx or a dropped connection → the menu entry is gone, the store has nothing, and the next `load()` (`colour.ts:143`, "Keep the cache; the next poll retries") replaces the cache with the server's empty answer. The choice is unrecoverable. The new `if (userSet && !sessionId) return;` guard at `terminals.ts:324` shows the team already understands this shape; it just does not cover the failure case. Fix: have `set()` return whether the write landed and `return` from the widget's callback when it did not, exactly as the `!sessionId` branch does.

- **[MAJOR] The write-back attributes a hand-set colour to a conversation the terminal may not be running.** `sessionId` at `terminals.ts:303-306` falls back to `sessionForCwds(...)` - the project's *representative* conversation - and line 316 writes the user's colour under that guessed id. `colour.ts:99` warns about exactly this ("resolving colour by row tints every terminal of a project with the representative's colour"). Colour one Claude terminal whose probe returned no `session_id`, and the representative conversation's stored colour is overwritten and every other terminal of that project takes the new tint. Pre-existing for `derived`/`none`, but the change puts Claude - the only provider with a colour of its own to lose - onto the same path. Fix: gate the write-back and the destroy-guard on `info.session_id` alone; keep the cwd fallback for *painting* only.

- **[MAJOR] Two canonical docstrings now state the opposite of what the code does.** `colour_store.py:5-8` still reads "the write-back beats the default everywhere except a ``native`` provider, where the assistant owns its own colour (acc-crit 'Override precedence')" - the exact clause the change rewrote. `routes.py:514-516` still reads "except against a ``native`` provider, whose colour store refuses every write (``ColoursHandler``)" - `ColoursHandler` refuses nothing now. These two files are where the next reader goes to learn the ladder; requirement 4 is that both tiers resolve it identically, and the prose tier disagrees with both. Fix: reword both to the ladder as shipped.

- **[MINOR] The server-side branch inheritance still skips `native` wholesale, where the client now inherits the hand-set override.** `routes.py:549` gates on `colour_source != "native"` and inherits *nothing*; `panel.ts:930-934` inherits `this._colours.get(parentId)`. Unreachable today - `SERVER_MINTED_FORKS = frozenset({"server-copy"})` (`registry.py:51`) and Claude is `native-flag`, so `BranchHandler` answers 400 `fork_unsupported` for the only native provider - so no user perceives it. It is still the one place the two tiers resolve the ladder differently, and acc-crit line 248 ("For a native provider only a HAND-SET override is inherited") has no server implementation. Fix: drop the branch and pass `parent_default=None` for a native provider, so `inherit_colour`'s existing `get_colour(parent) or parent_default` yields exactly the override.

- **[MINOR] The two genuinely new frontend rules are untested at every tier.** The diff changes `terminals.ts` and `panel.ts` but adds tests only in Python plus a Playwright spec that issues three `page.request` calls and never opens the panel or a terminal. `src/__tests__/colour.spec.ts` covers `effectiveColour`, which the change did not touch. So "a native fork inherits only a hand-set override" and "never paint over an unattributed hand-set colour" ship with zero coverage - against a module whose own header (`colour.ts:9-11`) says the tint "regressed twice behind a green suite that never ran the logic". Fix: a jest test on `_inheritColour`'s branch and on the reconcile guard with a stubbed colourful-tabs API.

- **[MINOR] `TAB_COLOUR_IDS` duplicates the companion's colour order with nothing pinning them together.** `colour.ts:22-29` reimplements `COLOURS` from `lib/colours.js` and its comment concedes "The order is load-bearing: its localStorage records a user's menu choice as an INDEX into this list." If the companion inserts or reorders a colour, the user right-clicks Green and the conversation is remembered as Blue, silently, forever (now including Claude). The companion pins its own three copies with an anti-drift test; this copy is pinned by nothing. Fix: a jest assert `expect(TAB_COLOUR_IDS).toEqual(COLOURS.map(c => c.id))` importing from `jupyterlab_colourful_tab_extension/lib/colours`.

- **[MINOR] Up to 30 s of exposure between the click and the persistence.** Capture happens only on the `COLOUR_INTERVAL_MS = 30_000` tick (`terminals.ts:26, 272`). Colour a tab and close that terminal within the window: the companion's `runningChanged` handler calls `pruneDeadTerminalColours`, the localStorage entry goes, the reconcile never ran, and the choice never existed. Narrow but it is requirement 2's failure mode. Fix: reconcile on terminal-close and on tab class mutation, not only on the timer.

- **[MINOR] The ui-test leaves the store dirty.** `colour-override.spec.ts:50-61` sets `rose` on the seeded conversation and never releases it; only the third test defends itself by clearing first (line 82). Any later spec, or a rerun, sees a Claude conversation whose colour is an override rather than the assistant's. Fix: release in an `afterEach`.

- **[MINOR] (taste) `_inheritColour` takes three arguments to use exactly one.** `panel.ts:924-937` - `parentColour` is computed once at `panel.ts:785` and threaded through four call sites, then discarded whenever `colourSource === 'native'`; `parentId` is discarded otherwise. Passing the parent `ISession` and calling `this._terminals.colourFor(session)` inside the non-native branch is one argument, no threading, same behaviour. Requirement 5 asks for surgical; this widened a private signature at four sites to carry a value one path throws away.

## What works

- The destroy-guard at `terminals.ts:320-326` is the right instinct, correctly reasoned from the companion's `releaseMenuColour` behaviour, and correctly placed *after* the capture and *before* the paint.
- `_inheritColour` reading the raw store rather than the effective colour for native (`panel.ts:930-932`) is exactly right - a fork keeps its own `/color` and still honours a deliberate hand-set parent tint. Requirement 3 met.
- Nothing in core names a provider; both tiers branch on the capability flag alone. Requirement 4 holds in code (the divergence above is one stale gate, not a provider check).
- The Python ladder collapsed to one line (`routes.py:196-199`), and the store's `get_colour(...) or default` reads identically to `effectiveColour`'s `if (userSet) return userSet`.
