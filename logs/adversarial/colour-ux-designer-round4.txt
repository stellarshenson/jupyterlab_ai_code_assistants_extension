## (b) New friction

- **[MAJOR] A late-resolving menu open retargets the menu already on screen.** `panel.ts:2004-2008` now assigns `this._activeSession = session` *after* the awaits, and Lumino's `Menu.open` is a documented no-op once attached (`node_modules/@lumino/widgets/dist/index.js:6504-6509`). Two right-clicks inside the async window - which is exactly what a user does when the first right-click appears to do nothing - therefore resolve as: whichever call finishes *last* wins `_activeSession` and re-runs `_rebuildContextMenu`, mutating the items of the menu that is already displayed, while the position stays where the first one opened and the row highlight (`:1411`, `:1429`) stays on the *last* row clicked. Concrete case: right-click branchy project A (extra branch fetch, finishes last), see nothing, right-click simple project B, menu appears anchored on B with B highlighted - and `Copy Path` copies A's path, `Reset Tab Colours` (no confirmation, by my own round-3 advice) releases A's colours. `Remove` and `Clean Up` are saved only because their dialogs name the project (`:577-584`, `:616-622`). This is introduced by this diff: before it, `_activeSession` was set synchronously and always matched the highlight. Fix: take a monotonic token at the top of `_openContextMenu` and bail before `_rebuildContextMenu` if a newer open has started.
- **[MAJOR] The release leaves the released colour on screen, and then removes its own affordance.** Because only hand-set ids are offered, the common flow - colour a project's tab sky, branch it twice, all three tabs sky - shows `Reset Tab Colour` (singular, `n === 1`), and one click reverts one tab while two keep wearing sky. Demonstrated at the API above: after releasing `A`, `B` and `C` are still `sky` and `overrides` is `[]`, so on the next right-click the item is *gone* (`panel.ts:1756`) - the user's reading is "reset is broken and there is no second try". There is no route back: the companion extension's own Clear is repainted from this store on the next reconcile (`terminals.ts:343-357`), so the only escape is to open each branch's terminal, hand-set a *different* colour, wait for the capture, and reset again - impossible for a branch whose terminal is never opened. I am not relitigating the origin split; the fix is scope disclosure at the two places it is currently silent: the item should tell the user that inherited tints are not included (or the release should re-tint the *branches* that inherited from a released parent, which is the semantics the label already implies), and `docs/acc-crit-jupyterlab-ai-code-assistants.md` "Colour origin" must record the limitation - an inherited colour has no user-reachable release - since the doc standard requires stated caveats.
- **[MAJOR] The 250 ms budget protects the wrong half of the menu.** `panel.ts:1980-1988` budgets the colour work, which I measured on a live server at 0.93-1.79 ms over ten samples (`GET providers/claude/colours`) - it was never the risk. The unbudgeted `await this._fetchBranches(session)` at `:1931-1933` is, and its `catch` (`:1966-1968`) only covers a *rejection*, not a hang: with no timeout in `requestAPI`, a suspended-then-resumed connection or a stalled proxy leaves a branchy row's right-click producing a highlighted row and no menu, forever, with Open/Copy Path/Remove unreachable. Mechanically pre-existing, but the round-3 fix asserts it is solved and it is not. Fix: move the branch fetch inside the same `Promise.race`, opening without submenus when it loses - which is exactly what the existing `catch` already does.
- **[MINOR] The count disappears at exactly one target, unlike every sibling.** `Clean Up Parallel Sessions (1)` (`:1761-1762`), `Switch and Manage Sessions (1)` (`:1942`), `Open Branched Conversation (1)` (`:1954`) and `Manage Sessions... (1)` (`:1789`) all print their number at one; `Reset Tab Colour` alone drops it (`:1752-1755`). An absent number reads as "this row's own colour", but the single target can be a branch the row does not represent and whose tab may not even be open - the case `colour-override.spec.ts:216-233` covers. Fix: keep the count whenever the target set is not exactly `[session.session_id]`.
- **[MINOR] The count silently narrows when the branch fetch fails.** `hasBranches` is false on a rejected fetch (`:1966-1968`), and `_resettableColours` then omits every branch id (`:1995-2001`), so the same row shows `Reset Tab Colours (3)` on one open and `Reset Tab Colour` on the next, with nothing saying the scope shrank and no dialog to catch it. Fix: for a row with `extra_sessions > 0` whose branch fetch failed, hide the item rather than offer an unknowable scope.

## Pinned questions

- **Does the counted label say the right thing now that it counts only hand-set colours?** It is arithmetically honest about what the click deletes and perceptually wrong about what the user sees. The count is of store rows the user has no surface for - nothing in the panel row, and nothing in the Manage Sessions popup (`src/core/popup.ts` contains no colour reference at all) - while the residue it excludes is, by construction, the *same colour*. "(2)" over five identically tinted tabs is a number the user cannot check against anything.
- **Is 250 ms the right trade for a right-click straight after colouring a tab?** Yes. Two round trips are needed (`load`, then `probe`) before `set` marks the override, and `set` marks it optimistically before its own POST (`colour.ts:206-215`), so the race is lost only above roughly 125 ms RTT - a remote hub, not a local server at ~1.5 ms. Losing costs one absent item on that first open; the background work completes anyway, so the next right-click is correct. That is a far better failure than the 30 s window it replaced. The budget is not the weak point of that hunk - the unbudgeted branch fetch beside it is (NEW-3).
- **Is the two-origin distinction visible to a user who never reads the code?** No. Two tabs wearing the identical tint differ only in a store flag; the sole signal is the item's presence and its count. That did not matter while the two origins behaved alike - it matters now, because the release treats them differently and the difference is what the user is left staring at (NEW-2). Making the distinction *visible* is the wrong fix (a swatch was declined, and per-conversation origin badges would be slop); making the *outcome* not need explaining is the right one.
