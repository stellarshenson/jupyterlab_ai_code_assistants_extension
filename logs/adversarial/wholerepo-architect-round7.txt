5. [MINOR] The saved-settings file is parsed 4-5 times per request, in the one
   file that states the read-once rule.  FACT - counted with an instrumented
   `load_jsonc`. No ledger entry.

   core/routes.py:204-241. `_user_settings()` globs the settings folder and runs
   `load_jsonc` (two regex substitutions over the whole file) on every call.
   `_provider_enabled` calls it; `_enabled_providers()` calls `_provider_enabled`
   once per registered provider.

   Instrumented count of `load_jsonc` invocations:
       StatusHandler.get     -> 4   (one per provider, routes.py:330-338)
       TerminalHandler.get   -> 5   (resolve() gate at :277, plus
                                     _tree_assistant -> _enabled_providers at
                                     :165-169)

   Twelve lines below, the sessions listing does the opposite and says so:
       routes.py:373  stored = colour_store.load_colours(provider.id)
                      "# Read once for the whole listing, not once per row."
   Four panels each run a 30 s colour loop (src/core/terminals.ts:27) probing
   every open terminal, so the multiplier is panels x terminals x 5.

   REMEDY, diff scale (REMOVES 3 of the 5 reads; ADDS no cache and no state):
   give `_provider_enabled` an optional `settings: dict | None` parameter and
   have `_enabled_providers()` read `_user_settings()` once and pass it down.
   Per request only - a memo across requests would need invalidation and would
   reintroduce the staleness the per-request read exists to avoid.

8. [MINOR] `namingStrategy` is a three-valued union of which the core reads two
   states.  FACT - over-engineering, not taste. No ledger entry.

   src/core/types.ts:29-35 declares `'launch-flag' | 'server-side' | 'none'`
   with a documented paragraph per member. The single reader in the entire core
   is src/core/panel.ts:907:

       if (this._descriptor.namingStrategy !== 'none') {

   Where the name then goes is decided by `forkStrategy` twenty lines later
   (panel.ts:930-940): `server-copy` puts it in the branch POST, `native-flag`

   `'server-side'`. Declare `namingStrategy: 'launch-flag'` on a `server-copy`

   with no parity test to catch it (finding 3).

   What stated requirement breaks if the union is deleted? None.

   REMEDY, diff scale (REMOVES ~15 lines): replace the union with
   `promptsForBranchName: boolean` on the descriptor, delete the
   `NamingStrategy` type and its doc block, and delete `NAMING_STRATEGIES` from
   src/__tests__/registry.spec.ts:68. One line changes in each of four provider
   modules. Keep each provider's own comment about where its name ends up - that
   is the documentation the union was standing in for, and prose cannot be
   mis-declared.
