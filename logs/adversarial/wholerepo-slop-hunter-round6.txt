1. MAJOR (FACT) - DEF-63's settings-dir plumbing is killed by no test; two
   mutations survive the whole pytest suite
   jupyterlab_ai_code_assistants_extension/core/routes.py:919,
   jupyterlab_ai_code_assistants_extension/core/migrate.py:92

   `migrate(providers, settings_dir=None)` falls back to
   `Path(jupyter_config_dir()) / "lab" / "user-settings"`. The ONE production
   caller - the migrate POST at routes.py:919 - passes `_user_settings_dir()`
   instead, which reads LabApp's configurable `user_settings_dir` trait, and the
   comment above it states the whole point: "migration reads the folder THIS
   server writes to rather than the default".

   Nothing asserts that. All nine tests in `test_migrate.py` monkeypatch
   `migrate.jupyter_config_dir` and call `migrate(...)` with no `settings_dir`,
   so every one of them exercises the FALLBACK. `test_settings_dir.py` proves
   `routes._user_settings_dir()` resolves the trait correctly, in isolation.
   No test binds the two ends together.

   Measured, in `fresh/`, full suite each time:
     M9  routes.py:919 -> `migrate.migrate(registry.providers().values())`
         (the argument dropped entirely)                    163 passed
     M10 migrate.py:116 -> `_legacy_settings(legacy.plugin_id, None)`
         (the parameter ignored inside)                     163 passed

   Both ends of the plumbing can be severed and the suite reports green. Under
   `--LabApp.user_settings_dir=/custom` (or `JUPYTERLAB_SETTINGS_DIR`) migration
   would read the wrong folder, find no retired-extension settings, mark itself
   done, and never look again - the exact silent failure DEF-63 was raised to
   prevent. The two runtimes' halves are each tested; the join is not.

   What would close it: one test that drives the migrate route (or calls
   `migrate.migrate(providers, tmp_path)`) with a settings dir DIFFERENT from
   `jupyter_config_dir()`'s default, and asserts the legacy keys are picked up
   from it. That test dies under both M9 and M10.

2. MAJOR (FACT) - `npx tsc --noEmit` clears the DEF-75 build-freshness guard
   while emitting nothing, which is the silent green the guard exists to prevent
   jupyterlab_ai_code_assistants_extension/tests/test_descriptor_parity.py:137

   `_require_fresh_lib` takes its build marker as
   `max(newest lib/*.js, tsconfig.tsbuildinfo)`. `tsconfig.json` sets
   `incremental: true` AND `composite: true`, and TypeScript 5.5 writes the
   buildinfo on a `--noEmit` run too. So a typecheck - which produces no `.js`
   at all - refreshes the marker and certifies `lib/`.

   Reproduced end to end in `fresh/` (mtimes preserved, `lib/` byte-identical
   to the repo's):
     A  pytest test_descriptor_parity.py                       4 passed
     B  append `export const _PROBE_ROUND6 = 1;` to
        src/core/colour.ts, pytest                             4 FAILED
        ("lib/ is older than src/: src/core/colour.ts was written after
         tsconfig.tsbuildinfo")
     C  npx tsc --noEmit                                       exit 0
        tsconfig.tsbuildinfo mtime -> now; newest lib/*.js UNCHANGED;
        `grep -c _PROBE_ROUND6 lib/core/colour.js` -> 0
     D  pytest test_descriptor_parity.py                       4 passed

   Step D is the whole defect: four parity assertions comparing today's Python
   against a `lib/` that provably does not contain today's TypeScript, reported
   green. The guard's own docstring says "the failure this guard exists to
   prevent is a SILENT green, and a red that needs one documented command is a
   far cheaper mistake" - and the cheap mistake has been traded for the
   expensive one by a command every agent in this campaign runs. `npx tsc
   --noEmit` is in the baseline list of this very round.

   The ordering that hits it is the campaign's ordinary loop: edit `src/`,
   typecheck, run pytest. Nothing exotic is required.

   Note the blast radius is wider than the parity file: `scripts/generate-
   schema.mjs` reads `lib/providers/*.js` too, so a stale `lib/` also generates
   a stale `schema/plugin.json` - and the parity guard is the only thing that
   was watching.

   What would close it: use a marker the typecheck cannot forge. Either drop
   `BUILD_INFO` from the max and accept the known false positive DEF-75
   documented (its remedy is one command and the docstring already names it), or
   compare CONTENT rather than mtime - e.g. require that every `src/**/*.ts`
   has a `lib/**/*.js` newer than it, or hash the descriptor fields out of both
   `src/` and `lib/`. mtime plus a file tsc rewrites for a non-build cannot
   answer the question the guard asks.

3. MINOR (FACT) - the DEF-72 timeout surface has no production consumer, and the
   escape hatch its own comment prescribes has no user
   src/core/request.ts:29-55, :24

   `RequestTimeoutError` and `isRequestTimeout` are referenced by exactly one
   file outside `request.ts`: `src/__tests__/request.spec.ts`. Grep across
   `src/` for `isRequestTimeout|RequestTimeoutError|REQUEST_TIMEOUT_MS` outside
   `request.ts` returns the spec, plus two prose mentions in comments
   (`colour.ts:230`, `panel.ts:1104`). No caller branches on a timeout, so the
   rationale the class carries - "a caller that cannot tell the two apart cannot
   report either honestly" - describes a caller that does not exist. Today a
   timeout reaches the user as whatever the generic failure path shows.

   DELETE-TEST, in `mut/`: removed `isRequestTimeout` and its docblock.
     npx tsc --noEmit -p tsconfig.json            exit 0
     npx jest                        6 suites pass, 112 passed;
                                     only request.spec.ts fails to compile
   The predicate is held alive solely by the test written for it.

   The second half is the same shape and matters more. The docblock on
   `REQUEST_TIMEOUT_MS` says the two N-bounded routes are covered because "a
   caller that knows it is starting such a sweep passes its own `signal` and
   gets no ceiling from here". No caller passes a `signal` - grep for `signal`
   across `src/` outside `request.ts` finds three comments and no code. So the
   documented mitigation is unimplemented prose, and the project DELETE that
   runs one `codex` CLI invocation per conversation (0.7s measured, 30s worst
   case each) is hard-capped at 60s with no way to opt out. The ledger discloses
   that these routes can exceed the constant; it does not disclose that the
   escape hatch named in the source is fictional.

   Smallest honest close: either wire one caller (the project DELETE) to its own
   `AbortController`, or delete the sentence and the unused predicate and say
   plainly that the N-bounded routes are capped like everything else.

4. MINOR (FACT) - the core-neutrality guard's comment stripper truncates at the
   first `//` even inside a string, and five lines in the core sit behind it
   src/__tests__/core-neutrality.spec.ts:80-90

   `stripComments` drops everything from the first `//` on a line, with no
   awareness of string literals. `src/core/icons.ts` carries five template
   literals containing `xmlns="http://www.w3.org/2000/svg"`, so everything after
   the scheme separator on those five lines is invisible to the scan.

   Measured, in `mut/`: injected a live branch onto icons.ts line 15, AFTER the
   `//` of the xmlns URL -
     `data-x="${false ? 'kimi' : ''}"`
   `npx jest core-neutrality` -> 19 passed. The guard whose docstring says "the
   source itself is the assertion" does not see it.

   No live violation exists today - I rescanned all of `src/core/*.ts` with a
   stripper that only honours a `//` not preceded by `:`, over
   claude|codex|kimi|gemini|anthropic|moonshot, and it found nothing. So this is
   coverage, not a breach, which is why it is MINOR. The one-line close is to
   ignore a `//` preceded by `:` (or to strip strings before comments).
