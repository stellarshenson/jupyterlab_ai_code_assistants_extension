## (b) New defects

**1. [MAJOR] The generation guard is stamped after the state it protects: a superseded open rewrites the open menu's branch submenus, and can make "Reset Tab Colours" drop another project's colours** - `src/core/panel.ts:2003` guards, but `branches()` writes `this._lastBranches` (`:1948`), `this._lastBranchesCurrent` (`:1949`), `this._switchSubmenu` (`:1955-1964`) and `this._openBranchSubmenu` (`:1967-1978`) with no generation check anywhere between `:1941` and `:1984`. The comment at `:1929-1932` - *"A superseded open must touch nothing"* - is false as written.

FACT for both halves.

Lumino behaviour TESTED in isolation (`.../scratchpad/r5/lumino.test.js`, passed under the project's own jest base config): clearing and refilling a submenu whose PARENT menu is attached leaves the parent on screen and swaps the visible items and the submenu title - `expect(parent.isAttached).toBe(true)` and `expect(sub.items.map(i => i.label)).toEqual(['A-branch-1'])` both hold. So the loser's late write is silent, not self-announcing.

Scenario (a), display. Row A branchy with a slow `list_branches` (400 ms - large store, or any latency); row B branchy and fast.
1. t=0 right-click A. `_openContextMenu(A)` gen=1, awaits `_fetchBranches(A)`.
2. t=250 the budget (`MENU_COLOUR_BUDGET_MS`, `:58`) expires, gen still 1, so A's menu opens with `branchesKnown=false` → `_resettableColours = []`, no submenus.
3. t=300 right-click B. gen=2, B's fetch returns in 20 ms, submenus filled with B's conversations, `_rebuildContextMenu(true)`, `_activeSession = B`, menu opens on B.
4. t=400 A's fetch resolves. Its continuation runs `:1948-1978` **before** reaching the guard: B's on-screen "Switch and Manage Sessions (N)" and "Open Branched Conversation (N)" now list **project A's** conversations, with A's counts. Clicking one calls `_switchBranch(B, <A's id>)` → `store.switch` cannot find `<A id>.jsonl` under B's project dir (`providers/claude.py:855-857`) → 404 → the user is told *"That conversation no longer exists - the list has been refreshed."* about a conversation that exists. "Manage Sessions" (`:2038-2039`) shows A's list under B's project name.

Scenario (b), destructive. Same two rows, but A's fetch lands inside B's own pre-guard window - i.e. after B's `_fetchBranches` resolves and before B's `colours` promise (`:1988-1991`, a `load()` plus a `reconcileColours` that probes every open terminal) settles or the 250 ms timer fires:
- B's locals are correct (`hasBranches = true`), but `_resettableColours` at `:2017-2018` reads the **instance** fields, which A has just overwritten.
- The menu opens on B showing "Reset Tab Colours (3)"; `execute` (`:1759`) passes those ids to `_colours.forget`, and `drop_colours` is keyed by provider, not by project (`colour_store.py:147-154`) - so **project A's hand-set colours are dropped** while the user is looking at project B's row. No undo; the user must re-pick each.

Fix: move the check inside `branches()`, immediately after `await this._fetchBranches(session)` and before line 1948, and keep `data.branches`/`data.current` in locals until the guard at `:2003` has passed - then assign the instance fields and build the submenus. The guard as placed covers only the three statements after it.

**2. [MAJOR] `set` still takes an unordered whole-map snapshot - a failing write, or a `load()` landing mid-write, wipes a concurrent successful capture from the cache and leaves an override marker with no colour** - `src/core/colour.ts:209` and `:262` (`const rollback = this._snapshot()`), `:291-298` (`_snapshot` copies and restores both maps entire), `:174-183` (`_absorb` replaces both entire).

FACT, three repros run against the transpiled `src/core/colour.ts` with a stubbed `requestProvider` (`.../scratchpad/r5/t1.js`, `t2.js`, `t3.js`).

Reachability: `reconcileColours` fans out with `Promise.all(widgets.map(...))` (`terminals.ts:412-416`), so N open assistant terminals with pending captures issue N concurrent `set` POSTs in one pass; `_fetch` fires `load()` independently at `panel.ts:545` while the 30 s colour loop (`terminals.ts:26`, `:272-275`) is mid-pass.

- **t1** - `set(A)` and `set(B)` in flight; B's POST succeeds (server holds both), A's rejects. `rollback()` restores the pre-A map: `get(A)=null, get(B)=null, isOverride(B)=false`, while `set(B)` returned `true`. `terminals.ts:334` read that `true` as `held`, so the tab was painted, and `_applyColour` → `setColour` → `releaseMenuColour` (`jupyterlab_colourful_tab_extension/src/index.ts:454-458`, `:189-207`) deleted the companion's localStorage entry. Nothing in the browser holds the colour any more.
- **t3** - single write, no failure. `set(A,'sky')` POST in flight; a routine `load()` GET answers a snapshot taken before the POST landed. `_absorb` replaces both maps → `set` then returns `true` with `get(A)=null` and `isOverride(A)=true`. The *same* reconcile callback proceeds to `_applyColour(widget, effectiveColour(sessionId, source, this._colours.get(sessionId), native))` at `terminals.ts:355-363` with a null cache entry - so the tab is painted with the **default** tint, not the colour the user just picked, and that paint releases the companion's record. Recovery is the next successful `load()`, up to 30 s.
- **t2** - the `isOverride(B) && get(B)===null` state it leaves is self-defeating for the release: `_resettableColours` (`panel.ts:2022`) filters on `isOverride`, so the menu offers "Reset Tab Colour (1)"; `forget` filters on `_colours.has(id)` (`colour.ts:258`), finds nothing present, and **returns `true` after issuing zero requests**. `_resetColours` (`panel.ts:932-945`) reports no error, then `_fetch` → `load()` restores the colour the server still holds and repaints it. The reset visibly did nothing and said nothing.

Fix: make both paths per-key, the same way the POST/DELETE answers were made per-key. `_snapshot` should capture and restore only the ids the request touched. `load()`'s `_absorb` should skip (or re-apply after) ids with a write in flight - a small in-flight `Set<string>` on the store is enough.

**3. [MINOR] "a native provider inherits only a HAND-SET override" is false for a branch of a branch** - `jupyterlab_ai_code_assistants_extension/core/routes.py:551-553` and `:586-588`, `src/core/panel.ts:950-953`, `docs/acc-crit-...md:232` and `:258`.

FACT, tested (`.../scratchpad/r5/t_native_inherit.py`): on Claude, hand-set A=sky → fork A→B stores B=sky **inherited** (`overrides == ['aaa']`) → fork B→C stores C=sky, because `inherit_colour` resolves the parent through `get_colour` (`colour_store.py:172`), which returns inherited entries too; the frontend's `native` arm does the same with `this._colours.get(parentId)` (`panel.ts:955-958`), and `ColourStore.get` (`colour.ts:141-143`) is likewise origin-blind. Final store: `{A: sky, B: sky, C: sky}`, `overrides: ['aaa']`.

The *code* is right - this is what acc-crit "Edge: branch of a branch" asks for - so this is a wording defect, not a behaviour one. It matters because it sits on the descriptor path a fourth assistant gets copied from, and because it is the same false-comment class as round-4's MINOR-6, which was fixed in three of its four places. Fix: say "only a STORED colour is inherited (the assistant's own default is not seeded)" in all five spots.
