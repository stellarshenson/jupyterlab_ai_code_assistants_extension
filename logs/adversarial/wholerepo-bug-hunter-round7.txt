1. [MAJOR] Every refusal this server sends renders to the user as
   "[object Object]"
=====================================================================
FACT - proven against the real @jupyterlab/services class.

  src/core/request.ts:137
      throw new ServerConnection.ResponseError(response, data.message || data);
  jupyterlab_ai_code_assistants_extension/core/routes.py - 13 sites, 10
  distinct codes, all shaped {"error": "<code>"} and none carrying "message":
      :275 provider_unknown   :279 provider_disabled  :284 cli_not_found
      :296 invalid_json       :302 <every bad_request>  :552 colour_store_unwritable
      :764/:794 session_not_found  :770/:858 terminal_service_unavailable
      :817 terminal_create_failed  :881 terminal_not_found  :886 terminal_has_no_pty

`data.message` is undefined for every one of them, so the whole parsed OBJECT
is passed as the Error message. `Error` stringifies it.

Reproduce:
  node --input-type=module -e "
  import { ServerConnection } from './node_modules/@jupyterlab/services/lib/index.js';
  const data = { error: 'remove_failed' };
  const e = new ServerConnection.ResponseError({status:400,statusText:'Bad Request'}, data.message || data);
  console.log(JSON.stringify(e.message));"
  ->  "[object Object]"

Failure scenario: the `gemini` binary disappears from the Jupyter server's
PATH (a venv rebuild, a nvm switch). The user clicks a row. `resolve()` answers
503 cli_not_found. `_openSession`'s catch is not a 404, so
`_notifyLaunchError` fires and the toast reads:

    Could not start a new session: [object Object]

Same for every other surface that prints the error text:
  panel.ts:672  Could not toggle favorite - try again. [object Object]
  panel.ts:717  Could not remove "demo" - try again. [object Object]
  panel.ts:803  Cleanup failed: [object Object]        (inside the modal)
  panel.ts:968/:995/:1044  Could not branch this session - try again. [object Object]
  panel.ts:1230 Switch failed: Error: [object Object]
  panel.ts:1266 Delete failed: Error: [object Object]

The 404 paths escape because `isResponseStatus(err, 404)` gives them their own
copy, and tornado's OWN 500s escape because tornado writes {"message": ...}.
What is lost is exactly the set of refusals this extension authored - the ones
that name a cause the user can act on.

Overlap: none in the ledger. DEF-53 closed "a failed launch erases its own
error message before it can be read" and DEF-81 defends `isRequestTimeout` on
the grounds that "a caller that cannot tell the server is slow from the server
is gone cannot report either honestly". Both are about the message reaching the
user. It reaches the user unreadable.

REMEDY (smallest terminal radius): one clause at request.ts:137 -
`data?.message ?? data?.error ?? data`. It lands where the shape mismatch
originates (the client reads `message`, this server writes `error`), fixes all
13 server sites and all 8 frontend surfaces at once, and touches no route, no
call site and no copy string. Do NOT rewrite the server's bodies to carry
`message` - that is 13 edits for the same effect and leaves the client still
unable to read a body from any other producer.

2. [MAJOR] The launch pre-flight runs the store's branch listing ON THE
   IOLOOP, freezing the whole Jupyter server for its duration
=====================================================================
FACT - measured twice, once with an injected delay and once with a real store.

  core/routes.py:760-765
      if session_id and isinstance(encoded_path, str) and encoded_path:
          known = provider.store.project_session_ids(encoded_path)   # <- inline

`project_session_ids` is `SessionStore.project_session_ids` -> `list_branches`,
which for Gemini reads and parses EVERY chat file of the project
(`gemini.py:_chats` -> `read_chat_meta` -> `path.read_bytes()` + `_parse_chat`
over the whole text), for Claude opens and tail-reads every transcript, and for
Codex reads the whole sqlite thread table or rglobs every rollout file.

The contract this violates is stated in the file it comes from:
  core/store.py:16-18  "every method is synchronous and may touch the
  filesystem or spawn the CLI. The routes run them off the IOLoop, so a slow
  store stalls one request, not the server."
And the same handler wraps the very next call, `launch_argv`, in
`run_in_executor` (routes.py:775).

Measurement A - real store, real jupyter_server, no mocks. A seeded Gemini
project of 20 conversations / 22.6 MB, a resume launch, and a 50 ms
`asyncio.sleep` canary on the same loop:

      launch answered at 202 ms (code 200)
      asyncio.sleep(0.05) canary woke at 191 ms

The canary is the proof: the loop could not get back to a 50 ms sleep for
191 ms. For those 191 ms every kernel message, notebook save, terminal
keystroke, contents call and other extension's poll in that server is stopped -
for every user of it.

Measurement B - the same harness with `ClaudeStore.list_branches` replaced by a
1.5 s sleep: entered 0.00 s, left 1.50 s, canary woke at 1.50 s, /status
answered at 1.52 s. Linear, with no ceiling but the store's size.

Scale: 191 ms for 22.6 MB warm-cache. A 100-conversation project is ~1 s of
whole-server freeze per row click, and it is paid on EVERY resume, because
`_doOpenSession` sends `encoded_path` and `session_id` together
(terminals.ts:147-155).

Overlap: DEF-82 logs `MigrateHandler.post` as "the one route that does its work
on the IOLoop" and states that "every other handler in routes.py hands its
filesystem work to run_in_executor (seven call sites)". That statement is
FALSE, and this is the site it missed. DEF-82 was deferred as having "no
observable symptom", which is true of the migration route (O(4) small JSON
reads) and not true of this one, which is N-scaling and measurable. Per the
corrected rule, an entry whose recorded mechanism is wrong is itself a finding:
DEF-82's enumeration is wrong.

REMEDY: wrap the one call in the executor the handler already has, in the
handler that already awaits one -
      known = await loop.run_in_executor(None, provider.store.project_session_ids, encoded_path)
with `loop = asyncio.get_running_loop()` hoisted above the pre-flight instead of
below it (routes.py:773). Two lines, one function, no contract change, no new
surface. It leaves `TerminalHandler`'s deliberate synchronicity alone - that one
is bounded and measured at 0.4-2.4 ms (see Tested and cleared).

3. [MAJOR] The colour queue's backlog grows without bound: the poll
   enqueues at 1/30 s and the queue drains at 1/60 s
=====================================================================
FACT - measured against the shipped lib/core/colour.js with a stubbed transport.

Three constants that were each chosen soundly on their own:
  src/core/panel.ts:66     POLL_INTERVAL_MS      = 30_000
  src/core/request.ts:31   REQUEST_TIMEOUT_MS    = 60_000
  src/core/colour.ts:238   _run - one request of this store on the wire, ever

and one call that binds them:
  src/core/panel.ts:649    void this._colours.load().then(() => reconcileColours())
  src/core/panel.ts:2554   setInterval(... this._fetch() ..., POLL_INTERVAL_MS)

`_fetch` has no in-flight guard, so against a server that accepts the
connection and never answers, one `load()` is APPENDED to the serialised chain
every 30 s while the chain retires one every 60 s. The queue length grows at
1 per minute for as long as the condition lasts.

Reproduce (1000x time compression - 60 ms client ceiling, 30 ms poll):
  node run.mjs   # lib/core/colour.js with requestProvider stubbed to hang
      polls fired while the server hung : 20   (= 600 virtual s, 10 min)
      requests actually issued          : 21   (one per 60 virtual s)
      isPending immediately after pick  : true
      user's capture waited             : 668 virtual seconds

Failure scenario: a JupyterHub proxy stops answering for ten minutes. The user
picks a tab colour. The POST does not reach the wire for eleven minutes. For
that whole time `isPending(sid)` is true (colour.ts:174, counted from the CALL
by design, DEF-30's note), which means:
  - panel.ts:2450 - the release affordance is withheld from that conversation
  - panel.ts:1110 - `_inheritColour` sees `isPending` and awaits `load()`, i.e.
    the entire backlog, so `_branchByNativeFlag` (panel.ts:971) does not return
    and `_watchForBranch` is never armed. The terminal is already open; the
    branch simply never surfaces in the panel.
The panel's ROWS recover the moment the server does - the sessions GET is not
queued - so the user sees a working panel whose colours, captures, releases and
fork inheritance are stuck for as long as the outage lasted.

Overlap: DEF-30's closing note says "The ceiling is per request, so K ops queued
behind a dead server wait K times it, not it" (repeated verbatim at
colour.ts:230-233). That prices K as a given. The evidence here is that K is not
a given: nothing bounds it, because the producer is twice as fast as the
consumer, and the `isPending`/`_inheritColour` consequence is not recorded
anywhere.

REMEDY (smallest): an in-flight guard on `_fetch` - the poll skips a tick while
the previous one is unanswered. One boolean field and two lines in
`panel.ts:_fetch`. It caps the backlog at 1 without touching the store, the
chain, the timeout constant or the deliberate `isPending`-from-the-call
semantics. State, do not mandate: the wider move is to make the poll's `load()`
coalescing (a queued load that is not yet sent is the same load), which is a
change to `ColourStore` - the object with this ledger's worst regression
history - and is not warranted by the evidence above.

4. [MINOR] Clean Up Parallel Sessions answers "Cleanup failed" when there is
   nothing left to clean
=====================================================================
FACT - driven against a live jupyter_server.

  src/core/panel.ts:2132  isVisible: () => (active()?.extra_sessions ?? 0) > 0
      - read off the row, up to 30 s stale
  src/core/panel.ts:775-788
      const listed = await this._fetchBranches(session);   // fresh, may be empty
      const ids = listed.branches.map(b => b.session_id);  // -> []
      ... DELETE { encoded_path, session_ids: [] }
  Every store refuses an empty list:
      claude.py:907, gemini.py (delete_branches), codex.py:646
        "if not isinstance(session_ids, list) or not session_ids: return None"
  -> routes.py:435  bad_request("remove_failed")

Reproduce:
  DELETE providers/claude/sessions  {"encoded_path": "<p>", "session_ids": []}
  ->  400 {"error": "remove_failed"}

Failure scenario: the user cleans up parallel sessions in one browser tab, then
does it again in a second tab whose rows are 20 s old. The menu item is still
offered (stale `extra_sessions`), the confirm dialog promises to remove N, and
the progress modal ends on "Cleanup failed: [object Object]" (finding 1) for an
operation that had nothing to do and no failure.

REMEDY: return early in `_cleanupParallel` when `ids.length === 0` - set the
modal message to "Nothing left to clean up." and refetch. Four lines in one
method, in the branch that already owns the modal's text. Leaves the server's
refusal of an empty list alone, which is correct: an empty selection IS an
invalid delete request.

5. [MINOR] Two of three per-file metadata caches have no cap; the third does
=====================================================================
FACT - grep-verified across the three stores.

  claude.py:131-132,192-193   _tail_cache, _TAIL_CACHE_MAX = 1024, cleared wholesale
  gemini.py:116,327           _meta_cache          - no cap, no eviction
  kimi.py:73                  _message_count_cache - no cap, no eviction

All three are module-level and live for the server process. `read_chat_meta`
(gemini.py:315-328) inserts one entry per chat file it ever stats and removes
none - including entries for conversations the user has since deleted, whose
key can never be hit again.

Failure scenario: a long-lived server with a Gemini store of several thousand
conversations accumulates several thousand parsed-metadata dicts that no read
will ever consult again. Honest sizing: the value is small (id, summary, kind,
count, truncated first prompt), so ten thousand conversations is single-digit
megabytes - the cost is the asymmetry, not the memory. It is called out here
because the same file family already solved it once, three lines away.

REMEDY: the sibling's own three lines, copied to each - a `_MAX` constant and a
`clear()` when it is reached. Nine lines total across two files, no behaviour
change (the cache is a memo; rebuilding costs one read per file in use, which
is exactly what claude.py's comment already argues).


=====================================================================
TESTED AND CLEARED - do not re-raise these
=====================================================================
* Colour-queue DEADLOCK. Read every queued body (`load`, `set`, `forget`) and
  every caller of the three across panel.ts and terminals.ts. No queued op
  calls another; `inherit` (colour.ts:382) delegates to `set` from outside the
  chain, as documented. `forget`'s filter calls `isPending`, which is a plain
  map read, not a queued method. The DEF-73 guard's blind spot for `inherit` is
  real (DEF-83) but nothing exploits it today.

* Does `_applyColour(widget, null)` destroy the user's tab colour when a
  capture fails? NO. Read the companion's source:
  node_modules/jupyterlab_colourful_tab_extension/lib/index.js:381-388 -
  `releaseMenuColour` runs only when `colourId` is TRUTHY, so clearing our tint
  leaves the companion's localStorage record intact and
  `refreshAllTabColours` repaints it. The strip-then-retry loop in
  terminals.ts:340-361 is recoverable, as its comment claims.

* Does `ServerConnection.makeRequest` forward `init.signal`? YES.
  node_modules/@jupyterlab/services/lib/serverconnection.js:198 builds
  `new settings.Request(url, {...settings.init, ...init})`, and the Request
  constructor reads `signal`. The DEF-72 timeout is genuinely armed.

* Is `TerminalHandler`'s deliberate synchronicity a stall? NO, at this size.
  Measured against the real ~/.claude (111 project dirs, 5510 transcripts,
  4.3 GB): `ClaudeStore.default_colour` 0.4-2.4 ms,
  `_expand_short_session_id` 1.0 ms. The docstring's "bounded filesystem work"
  holds. Its `<sid>.jsonl` component is a literal, so the glob is one stat per
  project dir, not a walk.

* Is the per-request settings read a cost? NO. `_provider_enabled` measured at
  0.055 ms against a 5.4 KB schema-commented settings file; a terminal probe
  pays five of them = 0.27 ms.

* Is `cwd` honoured by `terminal_manager.create`? YES - terminado
  `TermManagerBase.new_terminal` reads `options.get("cwd")` and passes it to
  `PtyWithClients`. And `TERM` is set unconditionally in `make_term_env`, so
  the waiter's `clear` never errors for want of a terminfo entry.

* `_INIT_WAITER` grammar. Walked every expansion. Process substitution inherits
  the pty as stdin so `stty size` reads the right device; `read r c < <(...)`
  is a builtin redirect, so `r`/`c` land in the parent shell, not a subshell;
  the `-gt` guards degrade a non-numeric or zero size to 24x80 with stderr
  suppressed; `exec "$@"` never interpolates the argv. tests/test_init_waiter.py
  covers both timeout directions against a real pty. Nothing new here.

* Deletion paths. `ClaudeStore.delete_branches` (:897) and
  `GeminiStore.delete_branches` re-resolve the current conversation
  server-side and skip it, so a `keep` that moved between the branch fetch and
  the DELETE costs the user nothing and the survivor keeps its colour.
  `KimiStore.fork` (:548) rolls the copytree back on any OSError before the
  index line is appended.

* In-flight requests outliving a disposed panel. `_watchForBranch` /
  `_watchForNewBranch` guard on `this.isDisposed` at tick entry
  (panel.ts:1137, :1176); `startColourLoop` guards on `_disposed`
  (terminals.ts:274); a late `_fetch` writes into a detached DOM node that
  Lumino leaves in place, so it is wasted work rather than a throw. The one
  observable residue is an app-global `Notification.error` from a launch that
  was refused after its panel was disabled - cosmetic, not worth an id.


=====================================================================
JOURNEYS I COULD NOT WALK
=====================================================================
* RENDERED PROOF. Galata was off-limits for this run. Finding 4's user-visible
  string ("Cleanup failed: [object Object]" in the progress modal) and
  finding 1's toast text are both traced through the code and proven at the
  Error-construction level, not photographed. What I would have run:
  a spec that stubs `DELETE providers/<id>/sessions` to 400 {"error":"x"},
  opens the cleanup modal, and asserts the modal's text does NOT contain
  "[object Object]" - green today would mean the finding is wrong.
* MULTI-USER. Finding 2's blast radius ("one user's click freezes every user")
  is an inference from single-process asyncio, measured on a single-user
  server. The mechanism is the same; the number of victims is not measured.
* COLD PAGE CACHE. All filesystem numbers are warm-cache. Cold, they get worse,
  never better, so the findings stand at their measured floor.
