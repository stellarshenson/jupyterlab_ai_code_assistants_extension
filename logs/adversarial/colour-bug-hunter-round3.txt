## (b) New defects

**1. [MAJOR] A colour write the server could not persist is answered 200, and `set()` believes it - the paint then destroys the colour** - `jupyterlab_ai_code_assistants_extension/core/colour_store.py:46-52` (`except OSError: pass`) and `core/routes.py:478-479` (`set_colour(...)` then `_finish_store(...)` unconditionally); client side `src/core/colour.ts:183-193` returns `true` on any non-throwing response and discards the body.

TESTED, FACT. With `write_json_atomic` raising `OSError(ENOSPC)`, `POST providers/claude/colours {"session_id":"abc","colour":"mint"}` returns **200** with body `{"colours": {}}` and `get_colour("claude","abc") is None`. (Scratch test at `/tmp/claude-1000/-home-lab-workspace-private-jupyterlab-jupyterlab-ai-code-assistants-extension/0257fef0-9212-4c10-ab11-3a300a3b5938/scratchpad/conc/test_save_fail.py`, passed.)

Failure scenario - state dir full, read-only, or root-owned after one `sudo jupyter` run:
1. User right-clicks a Claude terminal tab → Green. Companion stores `terminal:N`→3 and paints mint on the tab element (`lib/index.js:310-316`).
2. Within 30 s `reconcileColours` runs: `userSet='mint'`, `observedId=C`, cache empty → `set(C,'mint')` → POST → `_save` swallows the OSError → 200 → **`set` returns `true`** → `held=true` (`terminals.ts:325-329`).
3. `_applyColour(widget,'mint')` → `api.setColour` with a truthy colour → `releaseMenuColour(widget.id)` deletes the localStorage entry (`lib/index.js:172-182`) - the last surviving record of the choice.
4. Next poll (`POLL_INTERVAL_MS = 30_000`, `panel.ts:56`): `_fetch` → `colours.load()` → server answers `{}` → cache wiped → repaint from `/color`. The colour is gone, nothing reports anything, and no server log line exists either (`colour_store.py:52` is a bare `pass`).

Same hole on the release: "Reset Tab Colour" reports success, the override stays on disk, and the tab flips back at the next `load()`.

Fix: the response body already carries the authoritative map for exactly this purpose (`routes.py:440-442`) - have `ColourStore.set` verify against it (`data.colours[sessionId] === colour`, or absence when `colour` is null) instead of treating "did not throw" as confirmation. Cheaper still, make `_save` propagate: `colour_store._save` swallowing `OSError` and `ColoursHandler.post` answering 200 regardless is the actual lie. Either fix is testable at the Jest tier with a mocked `requestProvider` returning a map that omits the id - which is also the test that would have caught this in round 1.

**2. [MINOR] A failed reset is silent - `_resetColours` erases its own error two lines later** - `src/core/panel.ts:936` sets the inline error, `:939` calls `_fetch()`, and `_fetch` clears it unconditionally at `:536` (`this._setInlineError(null)`).

FACT, traced. Scenario: long-lived Lab tab whose `_xsrf` cookie has rotated - GETs still succeed, POSTs return 403. User clicks Reset → `set(id,null)` rejects → cache rolled back (`colour.ts:194-200`) → message set → `reconcileColours` repaints the *same* colour → `_fetch()` succeeds and blanks the message. The user sees the colour unchanged and no explanation. Every other action error in this panel survives up to 30 s (`_toggleFavourite:563`, `_removeProject:602`, `_branchByNativeFlag:834` - none call `_fetch` afterwards); this one is visible for one round trip. Fix: skip the `_fetch()`/`reconcileColours` tail when `written.some(ok => !ok)`, which is what the round-2 predecessor did, or re-set the message after the fetch.

**3. [MINOR] The context menu is now gated on a network round trip for every row, including single-conversation ones** - `src/core/panel.ts:1967` `await this._colours.load()`, unconditional, after the (already awaited) `_fetchBranches` at `:1927`. The handler at `:1400-1407` calls `e.preventDefault()` and then awaits.

FACT for the path, traced not run. Scenario: server unreachable (laptop resumed, kernel gateway restarting, VPN drop). Before this change a project with `extra_sessions === 0` opened its menu synchronously - no await between `preventDefault` and `_contextMenu.open`. Now `requestProvider` uses `fetch` with no timeout, so right-click yields neither the panel menu nor the browser's own until the request settles; on a hung socket, never. Fix: `Promise.all` the two fetches (they are independent - the branch list does not feed `load()`), which also halves the latency in the healthy case, or race the load against a short timeout and fall back to the cached map.

SUSPICION, same line: the window in which `_activeSession` (set at `:1405`) can be overwritten by a second right-click before the first `open()` lands now exists for every row, not just branchy ones. Two rapid right-clicks on different rows can leave the *visible* menu built from row A (`_resettableColours`, submenus) while `active()`-driven items - including **Remove** - resolve to row B. Settling test: throttle the server to ~500 ms and right-click two rows in succession.
