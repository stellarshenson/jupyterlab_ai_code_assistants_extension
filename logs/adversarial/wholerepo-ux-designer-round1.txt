VERDICT: DO-NOT-SHIP (19 findings) - the warning glyph that marks unsafe launches goes silent exactly when the unsafe mode is switched on, and the panel's two lowest-contrast text states are the first-run copy and the majority of rows.

## Findings

- **[CRITICAL] The unsafe-launch warning inverts once the setting is on** - `src/core/panel.ts:1661-1686` attaches `warningIcon` only to the *forced* variants (`Resume (Skip Permissions)`, `New … (YOLO)`, `Branch ▸ Skip Permissions`). But `_launchMode()` (`panel.ts:713-715` → `src/core/modes.ts:39-42`) returns the same token for the *plain* items whenever the settings boolean is true. So a user who ticked `providers.claude.dangerouslySkipPermissions` months ago right-clicks a row and sees `Resume` (no glyph) above `Resume (Skip Permissions)` (glyph) - two entries that build a byte-identical launch, where the unmarked one is the default and the marked one is redundant. The panel, the row, the terminal tab and the tooltip carry no other cue. Fix: drive icon and label from the *resolved* mode, not from `force` - when `_launchMode()` already returns a mode, the plain item gets the glyph and the suffix, and the forced duplicate is suppressed (it can add nothing). Same defect for Gemini `approvalMode: yolo`.

- **[MAJOR] Two text states sit below WCAG AA, and one of them is the entire first run** - `.jp-AiAssistantsPanel-empty` (`style/base.css:185-190`) renders at `--jp-ui-font-color3`: measured 2.68:1 on light, 3.57:1 on dark (AA needs 4.5:1). That is the only content a new user ever sees - "No Claude Code sessions found." plus the one instruction that gets them out of it (`panel.ts:1229-1240`). Separately, `.jp-mod-stale { opacity: 0.65 }` (`base.css:886-888`) multiplies through to the time column and branch badge (both `--jp-ui-font-color2`), giving 2.45:1 light / 3.22:1 dark - and "idle over a week" is most rows in the All section of any real workspace. Fix: `--jp-ui-font-color2` for the empty states (4.59:1), and move the stale dim off the row onto `.jp-AiAssistantsPanel-name` only, so the timestamp it is meant to de-emphasise stays legible.

- **[MAJOR] Every panel show blocks the panel for half a second** - `onAfterShow` calls `refresh()` (`panel.ts:254-257`), which raises the full-panel veil and holds it a minimum 500 ms (`panel.ts:204-222`). The veil is `position:absolute; inset:0; z-index:10` on the *root* (`base.css:449-457`), so it covers the header too: switching to the Gemini tab in a sidebar holding four assistant panels means 500 ms in which already-rendered rows are scrimmed and no row, filter or refresh button can be clicked. Two spinners fire for one action (button ring plus a 24px veil spinner). Fix: raise the veil only on a cold load (`this._sessions === null`); on a re-show, spin the refresh button alone and let the rows stay live.

- **[MAJOR] The launch modal's Cancel does not cancel** - `showLaunchSpinner` (`src/core/terminals.ts:34-53`) throws an app-wide modal scrim over all of JupyterLab on every non-reused row click, with `Dialog.cancelButton()`. The comment at `:32` admits it: "Cancel does not abort the request". A user who decides mid-launch that they picked the wrong project clicks Cancel, the modal goes, and seconds later a terminal opens and steals focus anyway. Fix: label it `Hide` (or `Continue in background`) so it names what it does; better, drop the modal and reuse the row's own `jp-mod-busy` spinner (`panel.ts:1354-1360`), which already exists for Remove and does not blank the app.

- **[MAJOR] The 30-second poll destroys keyboard focus** - `_render()` does `this._bodyEl.innerHTML = ''` (`panel.ts:1227`) on every fetch, and the poll fetches unconditionally every 30 s (`panel.ts:2122-2128`). The code carefully saves and restores per-section `scrollTop` (`:1210-1274`) but not the focused element, so a keyboard user who has tabbed to a row loses focus to `<body>` at an arbitrary moment and must tab back from the top of the panel. Fix: capture `document.activeElement`'s `encoded_path` before the wipe and re-focus that row after re-render - the same shape as the scroll restore already there.

- **[MAJOR] An enabled assistant whose CLI is missing reports only to the browser console** - `src/index.ts:242-248` writes `console.info` and nothing else; the comment one line above says "must not be a silent state". It is silent: the user ticks `Gemini: enabled`, gets no panel, and has no way to learn that the Jupyter server's PATH differs from their shell's. The rarer legacy-extension case gets a sticky `Notification.warning` (`index.ts:104-107`), so the common failure is the quiet one. Fix: same one-shot notification, naming the binary - `gemini not found on the server's PATH; no panel`.

- **[MAJOR] Four names for one object, all visible in a single right-click** - the menu offers `Open Branched Conversation`, `Switch and Manage Sessions`, `Branch Session`, and `Clean Up Parallel Sessions` (`panel.ts:1861, 1868, 1873, 1777-1779`); the popup then calls them "conversations" (`popup.ts:187`). Worse, "session" denotes two different things in the same menu: `New Claude Code Session` makes a conversation, while the panel titled "Claude Code Sessions" lists *projects* and `Remove from Claude Code` deletes a whole project's history. A user counting what `Clean Up Parallel Sessions (3)` will destroy has to reverse-engineer the vocabulary. Fix: one noun for the object - `conversation` - throughout: `Clean Up Parallel Sessions (3)` → `Delete Other Conversations (3)`, `Switch and Manage Sessions` → `Switch Conversation`, `Manage Sessions...` → `Manage Conversations...`.

- **[MAJOR] Both destructive items sit flush against the Branch submenu** - `_rebuildContextMenu` (`panel.ts:1931-1937`) ends `…submenu: Branch Session`, `cleanup-parallel`, `remove` with no separator. Lumino opens a submenu on hover, so the pointer travels down-right across `Branch Session` to reach its items; a slip lands on `Clean Up Parallel Sessions` or `Remove from Claude Code` - the two entries that delete history - with no visual break to slow the hand. The single separator in the menu is spent on the copy/branch boundary (`:1920`). Fix: add `{ type: 'separator' }` before `cleanup-parallel`.

- **[MINOR] Every row is a tab stop** - `row.tabIndex = 0` on all rows (`panel.ts:1340-1341`). A user with 40 projects tabs through 40 stops (plus 3 section headers) to leave the panel, and there is no arrow-key navigation. Fix: roving tabindex - one stop for the list, Up/Down to move within it.

- **[MINOR] The same project reports three different conversation counts** - the row badge shows `extra_sessions + 1` = 4 (`panel.ts:1371-1382`), the submenu titles show `branches.length` = 3 (`panel.ts:2053, 2065`), and the popup header shows `items.length + 1` = 4 (`popup.ts:183-187`), while `Manage Sessions... (3)` (`panel.ts:1806`) disagrees with the popup it opens. Fix: drop the counts from the two submenu titles (the items are listed right there) and count `Manage Sessions... (N)` over the same universe as the badge.

- **[MINOR] The star looks like a control and is not one** - the favourite star gets `title = 'Favorite'` but no handler (`panel.ts:1398-1404`), so clicking it launches a terminal like the rest of the row. Meanwhile the most common curation gesture - un-starring something you no longer care about - costs a right-click plus a menu hunt. Fix: make the star toggle the favourite (`stopPropagation` + the existing `_toggleFavourite`), which removes a step rather than adding a control; or delete its `title` so it reads as a marker.

- **[MINOR] Favourites vanish under a filter, and one empty state is unreachable** - `_render` only draws the section when `favourites.length > 0` (`panel.ts:1256-1258`), so a filter that matches no starred project removes the Favorites heading entirely - the user cannot tell whether the filter excluded them or their stars are gone. The `'No favorites yet.'` branch at `panel.ts:1314-1318` can therefore never render, so a new user is never told the section exists or how to fill it. Fix: render the section whenever any favourite exists, and let its empty body say `No matches.`

- **[MINOR] The empty and no-match states repeat themselves** - the first run stacks two italic grey lines (`panel.ts:1229-1240`) where the first ("No Claude Code sessions found.") only restates a visibly empty list; keep the actionable one. A filter that matches nothing prints `No matches.` once per section (`panel.ts:1309-1319`), so the user reads it twice under two `(0)` headings. Fix: delete the first empty line, and when the filter empties every section render one body-level line naming the query.

- **[MINOR] The time column overflows its own box on the oldest rows** - measured in Chromium against the stock light tokens: `11mo ago` renders 47.4px inside the `width: 4em` = 43.3px box (`base.css:869-876`), spilling 4px into the row's right padding, so the column the comment promises is "fixed-width right-aligned" is ragged exactly on the rows that use the longest label. Its twin `.jp-AiAssistantsPanel-branchTime` (`base.css:734-742`) also carries `font-variant-numeric: tabular-nums`; the panel's does not. Fix: `4.5em` plus `tabular-nums`, or drop the redundant " ago" suffix.

- **[MINOR] The + button never names the folder it will create in** - `newBtn.title` is the constant `New Claude Code session in the current folder` (`panel.ts:284`), and the target is the *file browser's* path (`_currentFolder`, `panel.ts:746-749`) - which lives in the opposite sidebar and may be collapsed. The user clicks a button in the right panel and a session is created somewhere they cannot see. Fix: build the title from `_displayPath(this._currentFolder())` so it reads `New Claude Code session in notebooks/analysis`.

- **[MINOR] The popup's only exit says "Cancel" after the deletes are committed** - `popup.ts:135` gives the Manage Sessions dialog `Dialog.cancelButton()`, so a user who has just deleted six conversations and read "6 moved to trash" must press *Cancel* to leave, which reads as an offer to undo. The cleanup dialog in the same feature gets this right with `Dialog.okButton({ label: 'Close' })` (`panel.ts:655`). Fix: `Close` here too. While there: the cleanup dialog stays up on success demanding a dismissal click for an outcome the row already reflects (`panel.ts:690-694`) - auto-dispose on success and keep the modal for the failure branch.

- **[MINOR] README promises three presentation modes; there are two** - `README.md:43` says "label rows by session name, folder name, or path", while `schema/plugin.json:8-14` enumerates `name` and `path` only (folder name is the *fallback* inside `name`). A user goes to Settings looking for the third option. Fix: "by session name or by path relative to the JupyterLab root".

- **[MINOR] Gemini ships two overlapping approval controls with a silent precedence** - `providers.gemini.yoloMode` (boolean) and `providers.gemini.approvalMode` (enum that already contains `yolo`) both exist (`schema/plugin.json:66-78`). Set `approvalMode: plan` and tick YOLO and the tick does nothing - correctly documented in a 40-word description, and invisible at the control. Fix: delete `yoloMode` for Gemini; the enum covers it, and the menu variant can force `approvalMode=yolo`.

- **[MINOR] (taste) Non-text indicators under 3:1, and one en-GB string in an en-US surface** - the live/remote dot at `opacity: 0.75` over `--jp-success-color1` measures 2.12:1 on light (`base.css:331-337`) and the favourite star at `opacity: 0.5` measures 2.17:1 (`base.css:390-401`); both are the sole graphic for their state, so 1.4.11's 3:1 applies. Both have `aria-label`/`title`, which is why this is MINOR rather than a hard fail. Fix: drop the opacity and use `--jp-success-color0` for the dot. Separately, the menu says `Add to Favorites` and the failure toast says `Could not toggle favourite` (`panel.ts:574`) - one word, one spelling.

## What works

- **Motion is calm and honest** - no pulses, no loops that are not genuinely indeterminate, and `prefers-reduced-motion` degrades the spinners to a still dimmed ring (`base.css:436-443`) rather than faking progress. The refresh floor is explicitly waived under that preference (`panel.ts:212-214`) - a rare and correct call.
- **Keyboard routes to the context menu exist and are the right ones** - both `ContextMenu` and `Shift+F10`, anchored on the row's own rect (`panel.ts:1442-1448`), so the menu that carries every non-default action is not mouse-only.
- **The permanent-delete arm-then-confirm in the popup footer** (`popup.ts:382-401`) - two steps that look different, a 4-second decay, disarmed by any selection change, and skipped entirely when the deletion is recoverable. Severity-calibrated rather than blanket-confirmed.
- **Errors are inline and per panel** (`panel.ts:508-521`, `base.css:161-171`), so one unreachable assistant server does not raise a modal over the other three panels.
