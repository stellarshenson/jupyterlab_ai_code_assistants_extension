- **NEW-2 (`branchesKnown` conflated failed with not-back-yet) - CLEARED.** The flag has no occurrences left in `panel.ts`. `:1994` seeds the set with `session.session_id` unconditionally, so a timed-out or failed branch fetch narrows the scope to the row's own conversation instead of hiding the item. I re-measured `claude agents --json` on this machine at **299 / 315 / 320 ms**; against `MENU_STATE_BUDGET_MS = 1_500` (`:62`) that is 4.7x headroom, so the reachable-timeout half of the finding is closed as well. ## (b) New friction

- **[MAJOR] NEW-A - the right-click is now silent for up to 1.5 s, and an impatient second click makes it 3 s.** `panel.ts:1968-1975` races the branch fetch *and* `_colours.load()` → `reconcileColours()` against `MENU_STATE_BUDGET_MS = 1_500` (`:62`), and nothing appears on screen until it settles. The only feedback in that window is `_setActiveRow` (`:1598-1604`) switching the row from `--jp-layout-color2` to `--jp-layout-color3` (`style/base.css:305-311`) - and the cursor is already over the row, so `:hover` had already painted color2; the delta is one theme step. Direct manipulation reads as broken past ~1 s without a busy signal, so the user right-clicks again - which bumps the generation, makes the first open return at `:1976-1978` without ever opening a menu, and starts a fresh 1.5 s budget with a fresh `load()` + `reconcileColours()` (no in-flight dedup on either). Total silence from the first gesture reaches ~3 s, and every further click resets it. At 250 ms this cost 250 ms per retry; the round-5 raise is what made it a user-visible stall. Fix: keep the 1.5 s ceiling (it is the right hang bound at 4.7x the measured 320 ms spawn) but stop being silent - set a progress cursor, or a busy state on the row, once the open passes ~150 ms. If a busy affordance is off the table, drop the ceiling to ~800 ms, still 2.5x the measurement and inside the flow-of-thought limit.
- **[MAJOR] NEW-B - "the extension remembers it for that conversation" is false on the Codex and Kimi terminals users spend the most time in.** `README.md:37` states the write-back unconditionally. `src/core/terminals.ts:322` keys it on `info.session_id` alone, and `:329-346` bails to `_applyColour(widget, null); return;` when that is null - no store write, ever. `info.session_id` is `session_id_for_pid` (`core/routes.py:140`, `:787`), which for Codex and Kimi is argv-only (`core/store.py:363-375`): a brand-new conversation launches as bare `codex` / bare `kimi` (`providers/codex.py:686-690`, `providers/kimi.py:675-680`) and reads back None (`codex.py:705` "A cmdline with no resume id is a brand-new session (None)", `kimi.py:689` "A bare launch reads back as None"), as does a fresh `codex fork` terminal (`codex.py:703-704`). For the whole life of that terminal the user can pick a tab colour, watch it stay on the tab (the companion owns it), and get: nothing in the store, no inheritance by branches, no colour when the conversation reopens elsewhere, and no `Reset Tab Colour` on the row - with zero signal. On Codex and Gemini the store is the *only* colour mechanism, so this is the whole feature failing silently. Pre-diff this case worked: the write-back used the cwd-resolved `sessionId` (`git show HEAD:src/core/terminals.ts`, the `colourSource !== 'native'` branch). Narrowing to the observed id was the right call - it fixed round-1's guessed-conversation write - but it left a hole nothing tells the user about, and the new README sentence papers over it. Nothing in Galata covers it either: every case in `ui-tests/tests/colour-override.spec.ts` seeds the store over HTTP (`:82-92`) and only the *release* is driven through the menu, so the capture path the README describes is untested end-to-end. Fix: either qualify the README sentence (a colour set on a brand-new Codex or Kimi conversation is remembered once that conversation is reopened from the panel), or - better - make the row show the same absence the reset item does, so "not remembered" is visible rather than assumed.
- **[MINOR] NEW-C - the pre-1.0.0 caveat gives the remedy but not the cue that triggers looking it up.** `README.md:37` says "a colour carried over from a version before 1.0.0 has to be set on the tab once more before it can be reset", and the same bullet asserts the item is in the menu ("`Reset Tab Colour` in the session's right-click menu hands it back"). But `panel.ts:1761` hides the item rather than disabling it, so the upgrader's entire symptom is an *absence* against a README that says the item is there - which reads as "the docs are wrong" or "not shipped", never as "I am in the caveat". Answering the pinned question directly: the remedy itself is complete and mechanically correct (I traced it - `terminals.ts:329-332` fails the `isOverride` half, `:334` writes with `handSet` true, and the companion's colour commands have no `isToggled`, `jupyterlab_colourful_tab_extension/src/index.ts:358-379`, so re-picking the same colour is a real click), but it is unreachable from the symptom. Fix: one clause - "the item appears only while a colour you set by hand is stored" - which is also what makes the caveat legible.
- **[MINOR] NEW-D - the bullet names a per-conversation release; the item performs a per-project one.** `README.md:37` says "`Reset Tab Colour` ... hands it back" (singular, this conversation), and its second caveat talks only about branches the release does *not* touch. What the item actually does is release the hand-set colours of the row's conversation *and every branch of it* in one click (`panel.ts:1992-2001`), under the label `Reset Tab Colours (3)` (`:1756-1757`) - a name the README never uses, and a scope whose only warning on screen is the count. A user who set colours on three branch terminals reads the README, clicks once, and loses all three. Fix: "hands back the colours you set by hand on that project's conversations - the number on the item says how many".
- **[MINOR] NEW-E - the comment promises a recovery the code does not perform, and the user gets no retry.** `panel.ts:1966-1967` says "past the budget the menu opens on what is already cached, and the work completes for the next right-click". True for the colour half (`load()` mutates the store), false for the branch half: the timeout resolves the race, the late `Promise.all` value is discarded, `_fetchBranches` sends `cache: 'no-store'` and holds no client cache (`:1124-1129`), and `_lastBranches` is written only at `:1982` and `:2063`. So a project whose branch listing consistently exceeds 1.5 s never shows `Switch and Manage Sessions` or `Open Branched Conversation` on *any* open, with nothing on screen saying why and no way to ask again. Rare now that the budget clears the measured 320 ms by 4.7x, which is why this is MINOR rather than the MAJOR it was at 250 ms. Fix: correct the comment, and keep the fetched list even when it lost the race so the next open renders it.

## Answers to the pinned questions

- **Does the rewritten README bullet equip a user to recover a pre-1.0.0 colour?** Half. The remedy is correct and the gesture works (traced above). It fails on recognition - the item is hidden, so the symptom is an absence the bullet does not connect to the caveat (NEW-C) - and it omits that the conversation's terminal must be open for the re-pick to be captured at all (`terminals.ts:413-429` only walks live tracked terminals), which for a branch means going through `Open Branched Conversation` first. Two clauses close both.
- **Is 1.5 s the right ceiling for a right-click?** As a *hang* bound, yes - 4.7x my re-measured 299-320 ms is the right shape, and clipping at 250 ms would have dropped submenus from menus that used to wait. As a *silent* wait, no: 1.5 s with no busy affordance is past the point where a user assumes the click was lost, and the retry is punished rather than helped (NEW-A). Add the busy signal and 1.5 s is fine; keep it silent and it should be ~800 ms.
- **Does anything in the diff still promise the user something the code does not do?** Yes, three things, all in the one new README bullet: the unconditional write-back (NEW-B, the serious one), the singular per-conversation release (NEW-D), and - on the slop axis - the clause "which this extension no longer reads once the colour is stored" (`README.md:37`), which is user copy carrying an implementation justification, and an inaccurate one: `readUserSetTabColour` reads that storage on every pass (`src/core/colour.ts:54-58`); the entry is simply gone, because the companion deletes it when the API paints (`jupyterlab_colourful_tab_extension/src/index.ts:454-461`). Cut the clause to "the tab menu's own Clear will not release it". Everything else I checked is honest: the count states exactly what the click will change even in the narrowed-scope window, and the acc-crit Colour section now matches the code line for line.
