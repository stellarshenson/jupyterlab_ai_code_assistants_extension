## (b) New defects

**N1. [MINOR] The 30 s poll can move keyboard focus to a different row than the one it left, and scrolls the list to it** - `src/core/panel.ts:1261-1265` and `:1314-1322`.

`data-encoded-path` is not unique in the body: `_render` puts the same project into up to three sections (`:1295-1299`), all expanded by default (`:92-96`), and `_renderRow` stamps the attribute on every copy (`:1392`). `querySelector` returns the first in document order - the Favourites copy. Scenario: user tabs to a favourited project's row in the **All** section and scrolls; poll fires; focus lands on that project's **Favourites** row instead, and the bare `?.focus()` scrolls it into view, undoing `this._bodyEl.scrollTop = bodyScroll` set one line earlier. Fix: capture the section too (`closest('.jp-AiAssistantsPanel-section')?.dataset.section`) and scope the query to it, and use `focus({ preventScroll: true })` so the restored offsets stand. FACT.

**N2. [MINOR] Gemini's safest launch mode wears the danger triangle, labelled with a word that does not name it** - `src/core/panel.ts:1698-1701,1725,1899-1900,1938-1941` against `src/providers/gemini.ts:68-74`.

`_variantSuffix` falls back to `mode.title` because `approvalMode` declares no `menuLabel`, and `icon: () => (this._resolvedVariant() ? warningIcon : undefined)` fires for any non-default enum value. Scenario: user sets `providers.gemini.approvalMode: "plan"` - read-only, strictly safer than the default. Every plain menu item becomes `Resume (Approval mode)` / `New Gemini Session (Approval mode)` / `Normal (Approval mode)` with a warning triangle. Same rendering for `"yolo"`, which genuinely warrants it, so the marking no longer distinguishes the two. Fix: decide the glyph from a per-mode danger flag (or from the resolved *value* for an enum) rather than from "a mode resolved at all", and put the value in the suffix - `(plan)`, `(yolo)` - not the mode's title. FACT.

**N3. [MINOR] The new + button tooltip reads "in ." at the file-browser root** - `src/core/panel.ts:307-311` against `:1573-1578`.

`_displayPath` answers `'.'` for the root itself, and `'.'` is truthy so the `|| 'the current folder'` fallback never fires. Scenario: default JupyterLab, file browser at its root (the state every fresh session starts in) → hover + → *"New Claude Code session in ."*. The static title it replaced (`:312`) was correct there. Fix: treat `'.'` as empty at the call site, or have `_displayPath` answer `''` for the root and let the existing fallback do its job. FACT.

**N4. [MINOR] The missing-CLI notification fires for assistants the user never installed, and blames PATH for a failed status probe** - `src/index.ts:241,245-261`.

Two scenarios, both from `available` being false for reasons other than PATH:
- Fresh machine, one assistant installed. All four providers default to `enabled: true` (`schema/plugin.json:36-83`), so the first `reconcile()` raises **three** 8-second warning toasts naming binaries the user has never heard of. The console line this was promoted from was the right register for that.
- `probeStatus` fails - server extension not enabled, or a restart in flight - and sets `status = null` (`:130`). `statusFor` then answers null for every provider and `:241` reads that as `available = false`, so all four toasts claim "`claude` was not found on the Jupyter server's PATH" when the frontend never reached the server at all.

Fix: notify only when the status probe SUCCEEDED and the provider's own `available` is false (`probe !== null && probe.available === false`), and consider gating the toast on the user having explicitly enabled that provider rather than on the default-on state. FACT for both paths; the fresh-machine count is arithmetic off the schema defaults.
