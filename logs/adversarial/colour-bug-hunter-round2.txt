## (b) New defects

**NEW-1. [MAJOR] "Reset Tab Colour" is unreachable for every conversation that is not the row's current one** - `src/core/panel.ts:1728` (`isVisible: () => !!this._colours.get(active()?.session_id)`) and `:1730`. `active()` is the row (`:1600, 1392`), whose `session_id` is the project's pinned/current conversation - only `SwitchHandler` and `BranchHandler` write that pin (`core/routes.py:412, 548`). The write-back keys on the terminal's **observed** conversation (`terminals.ts:321`), which is deliberately allowed to differ.
Failure scenario (FACT, traced): project `branchy` has conversations A (current) and B. User right-clicks the row → "Open Branched Conversation" → B; `open-branch` calls `_openSession(s, undefined, B)` (`panel.ts:1774-1779`) and no pin is written. User colours that terminal's tab mint → store[B]='mint', painted, localStorage released. Right-click the row: `isVisible` reads `store[A]` → undefined → the item renders `lm-mod-hidden` (`@lumino/widgets/dist/index.js:7029-7031`). B's terminal is mint forever and, being Claude, its `/color` never shows again. The only way back is to *switch* the project's current conversation to B first - undiscoverable, and it changes unrelated state. Same hole for a fork whose id `_inheritColour` seeded but which the user then switched away from.
Fix: key the item on the conversation the reset should target, not the row - either offer it in the branch submenus with `args.session_id`, or make `isVisible` true when *any* of the row's conversations carries an override and reset the set.

**NEW-2. [MINOR] Reset deletes one of the two records the capture path reads, so a surviving companion entry silently re-applies the override** - `src/core/panel.ts:920-926`. `_resetColour` clears the server store only; nothing touches the companion's `jupyterlab-colourful-tab-colours` entry, which normally has already been consumed by `releaseMenuColour` during the capture paint. The window where both records exist is real: `terminals.ts:326` awaits the POST and `:345` paints afterwards, while `_applyColour` no-ops if the widget was disposed in between (`:383`) - the disposal check at `:399` is only before `apply`. Sequence: user colours the tab, closes it during the POST → store[B]='mint' and localStorage still holds it (the companion prunes only sessions the server stops listing, `lib/index.js:122-127`, and closing a tab does not stop the session) → user hits Reset → store cleared → user reopens that terminal → next pass re-captures mint and the reset is undone with no message. Narrow (FACT for the disposal window, traced not run); SUSPICION for the second reachable path, two browser windows on the same origin sharing localStorage while each holds its own `tabColours` map - settling test is opening two Lab tabs and colouring in one.
Fix: have the reset also drop the companion's entry, or accept it and say so in the docstring at `:917-919`.

**NEW-3. [MINOR] A poll-driven `load()` can clobber a just-acked write, and the paint then releases the localStorage backstop** - `src/core/colour.ts:157` (`this._colours = next`, wholesale replace) against `terminals.ts:324-353`. `_fetch` chains `load().then(reconcileColours)` (`panel.ts:539`), but the 30 s colour timer (`terminals.ts:272-275`) runs independently, so a GET issued before the POST landed can resolve after it. Self-heals on the next `load()` (the server does hold mint), so the cost is one poll interval - up to ~60 s - of the wrong colour, not permanent loss. Fix: merge into the existing map instead of replacing, or drop entries only when the loaded map is known newer than the last local write.
