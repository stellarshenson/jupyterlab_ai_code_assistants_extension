F1  CRITICAL  Kimi never recognises its own terminal - comm is
              "kimi-code", the store matches "kimi"
    jupyterlab_ai_code_assistants_extension/providers/kimi.py:227
--------------------------------------------------------------------

KimiStore sets `comm_name = "kimi"` and does NOT override `owns_pid`, so
identity is exact equality against /proc/<pid>/comm. The shipping CLI
renames itself.

Measured against the installed kimi 0.34.0
(/home/lab/.local/bin/kimi -> ELF), sampling /proc/<pid>/comm every 0.5ms
from exec:

  long-lived kimi comm sequence:
    [(0.2ms,'python'), (5.4ms,'kimi'), (10.6ms,'MainThread'),
     (674.5ms,'kimi-code')]
  owns_pid at steady state: False    comm_name = 'kimi'

The "kimi" window is 5ms wide and closes ~675ms after exec. Every probe the
extension ever issues lands after that.

End to end, launched exactly as LaunchHandler does
(routes._wrap_with_init([...]) under a pty, browser-style resize at +300ms,
sampled after 3s, no saved settings so all four providers are enabled):

  enabled providers: ['claude','codex','gemini','kimi']
  pty root comm: kimi-code
  _tree_assistant -> None None

The same harness identifies the other three correctly, which rules out an
artefact of the harness:

  codex  comm='codex'           -> codex
  claude comm='claude'          -> claude
  gemini comm='node-MainThread' -> gemini   (argv confirmation, DEF-24)

Blast radius, all of it silent:

  * TerminalHandler answers running:false, session_id:null, colour:null for
    EVERY Kimi terminal (routes.py:832-851).
  * TerminalManager.findForSession never matches, so step 2 of the reuse
    ladder is dead: every click on a Kimi row that is not a repeat click on
    the identical conversation inside one panel lifetime spawns ANOTHER
    terminal (terminals.ts:218-231, 130-142).
  * _eachAssistantTerminal returns early on !info.running, so the colour
    pass never touches a Kimi tab (terminals.ts:443). Kimi's descriptor is
    colour_source:'derived' - the whole point of that flag is a per-
    conversation hashed tint, and none of it will ever render. The tab
    write-back (readUserSetTabColour -> _colours.set) never fires either,
    so a colour the user sets by hand on a Kimi tab is never captured.

This is the identical failure gemini.py documents at length as DEF-24 and
solves with a comm CANDIDACY set plus an argv confirmation. Kimi got
neither. No test catches it: test_registry.py:138 only asserts
`isinstance(store.comm_name, str)`, and test_provider_stores.py monkey-
patches process_comm, so the suite certifies the wrong string.

Note the shape of the fix matters: "kimi-code" alone is as brittle as
"kimi" - the binary wore three different names inside 700ms. The gemini
pattern (candidacy set + argv element whose basename IS the CLI) is the
one that survives a rename.

F2  MAJOR  DEF-33 traded a 1-in-5 race for a narrower one that fails
           SILENTLY and PERMANENTLY: a client resize landing before the
           1x1 mark stalls 5s and execs the assistant at 1x1
    jupyterlab_ai_code_assistants_extension/core/routes.py:53-62
--------------------------------------------------------------------

The waiter's break condition is "the size is no longer 1x1". If the
browser's first set_size lands BEFORE the child's `stty rows 1 cols 1`, the
mark overwrites the client's size, nothing changes it again (the widget
sends one size on attach), the loop burns all 50 iterations and execs into
a 1x1 pty - with a client fully attached and rendering.

Reproduced deterministically (parent sets 30x120 immediately, never again):

  elapsed 5.15s
  child sees: "1 1"   then EXECED

versus the intended interleaving (resize at t+350ms): 0.42s, "30 120".

This is NOT DEF-47. DEF-47 is the no-client-ever-connects path, where 1x1
is a cosmetic consequence of an empty tab. Here the tab is live, the user
is looking at it, and the assistant renders into one cell for the rest of
its life - xterm only re-sends a size on a window/tab resize, so nothing
self-heals. The user's report will be "the terminal opened blank and hung
for five seconds".

Window width, measured on an idle box over 15 launches through the real
jupyter_server_terminals.TerminalManager:

  ms from create() returning to pty==1x1:
    [0.02, 1.59, 1.65, 1.59, 1.56, 1.58, 1.66, 1.74, 1.83, 1.84,
     1.42, 1.70, 1.65, 1.25, 1.68]        median 1.65ms

  ms from pty.fork() to pty==1x1, 20 runs: median 3.6, max 4.8

So the child must lose a ~1.6ms race against [serialize response -> HTTP to
browser -> terminal:open -> WS upgrade -> xterm mount -> fit -> set_size].
On an idle localhost the child wins comfortably. It is not structurally
guaranteed to: bash's startup is the part that gets delayed under CPU
pressure (CI, parallel Galata workers, a cgroup-throttled container), while
the already-queued HTTP response is not.

The mark is a level, not an edge, which is why the race is one-sided.
An edge the client cannot forge - e.g. wait for ANY size change from a
value the child records after marking, or have the child re-mark once if it
is still 1x1 after the first second - would close it without reintroducing
DEF-33's server-side resize.

Severity is MAJOR rather than CRITICAL only because the probability on a
healthy machine is low; the consequence when it fires is a dead terminal
with no error anywhere.

3. WHAT I LOOKED AT AND FOUND CLEAN
====================================================================

* ColourStore's write/read sequencing (colour.ts:161-372) - the
  _writeSeq/_readAbsorbed/_writeStart interlock is internally consistent;
  a superseded write neither applies its own result nor blocks the newer
  one; forget() filters on cache-or-pending so a capture on the wire cannot
  outlive the delete. _writeStart is never pruned (documented, one int per
  conversation).
* write_json_atomic - unique mkstemp name per write, fsync before replace,
  tmp unlinked on any exception. Orphan `<name>.XXXX.tmp` files after a
  SIGKILL are never swept, but nothing globs the state dir, so they are
  clutter only.
* set_colour / drop_colours / inherit_colour - the overrides set is always
  re-derived under `sid in colours`, so it cannot name an id the map lost.
  Read-modify-write is not cross-process atomic; within one server the
  handlers are synchronous on the IOLoop so it is serialised.
* index.ts lifecycle - stop() disposes both the command and the panel
  before any re-start, so addCommand cannot collide; LayoutRestorer.add is
  a Map set, not a throw; the 60s status interval is page-lifetime.
* Panel dispose ordering - clearColours() races ahead of _disposed=true by
  design; startColourLoop() re-checks _disposed so the timer cannot be
  rearmed after dispose.
* _render / _renderSection empty states - the only reachable empty section
  is Favorites under a filter, and it still renders 'No matches.'
* popup.ts delete path - `deleting` guard, arm/disarm timer, isAttached
  checks before touching shared state after the refetch await. Timers that
  fire after close touch detached DOM harmlessly.
* Settings gate cost - _enabled_providers() re-parses the user-settings
  file once per provider (4 parses; 0.27ms total with a realistic
  200-comment-line file). Negligible even on the synchronous probe route.
* gemini owns_pid against the real CLI on Node 26: comm 'node-MainThread',
  argv ['node','/home/lab/.local/bin/gemini'] -> True. The _NODE_COMMS
  candidacy set is correct for the Node actually installed.
