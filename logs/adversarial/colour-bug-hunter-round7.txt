## (b) New defects

**1. [MAJOR] Two overlapping GETs answered out of order: the newer absorb prunes `_writeStart`, so the older answer wipes the colour the write just stored** - `src/core/colour.ts:211` (`this._writeStart.delete(id)`), `:205-206` (the prune condition), `:226-227`.

FACT, tested. `r7/t1_ooo_get.js` drives the real `ColourStore` against a server that snapshots at service time:

```
set -> true | cache after set: sky
after load#2  : sky true
server        : {"colours":{"AAA":"sky"},"overrides":["AAA"]}
after load#1  : null false
```

Scenario. `load#1` is issued at t0 while the store is empty and its answer stalls. At t1 the colour loop captures the user's pick and `set(A,'sky')` (seq 1) lands - the tab is painted, which makes the companion extension delete its own localStorage record (`index.ts:458`), the last browser-side copy of the choice. At t2 `load#2` is issued (`asked = 1`) and answered: `_writeStart[A] = 1 <= 1` and not pending, so `:211` prunes A. At t3 `load#1`'s answer - a snapshot of the empty store - arrives with `asked = 0`, finds `_writeStart` empty, and takes the whole map: A is dropped from `_colours` and `_overrides`. `reconcileColours` then reads `readUserSetTabColour` as null (released at t1) and `_colours.get(A)` as null and repaints the tab with the assistant's default; `Reset Tab Colour` is hidden (`panel.ts:1766`, `:2017`). Recovered on the next successful `load()`, so the user watches the colour vanish and return over up to 30 s - the same end state and duration as round-6 MAJOR-1.

Reachability: FACT for the code path. Nothing serialises reloads. `panel.ts:551` fires `void this._colours.load()` from every `_fetch` (~10 call sites plus the 30 s poll at `:2100-2106`), `:188` fires one at construction, and `:1974-1976` fires one per context-menu open - and that last one is the path that then issues the write, via `reconcileColours`. Two loads in flight is the normal state at startup and at every right-click that overlaps the poll. SUSPICION only on how often the answers invert; HTTP/2 multiplexing and multi-socket HTTP/1.1 both permit it.

Fix, verified: the write sequence does not order READS. Give `load()` its own monotonic issue number, remember the highest one absorbed, and discard an answer older than it - a newer answer is strictly better, so dropping the straggler is free. I applied exactly that to a copy (`r7/fix/src/colour.ts`: `const issue = ++this._readSeq` at issue, `if (issue < this._lastAbsorbed) return;` at the top of `_absorb`) and re-ran the same script: `after load#1 : sky true`.

Scenario, and it is the window the 800 ms budget builds. The user picks a colour on the tab. The next reconcile issues `set(A,'sky')`; the POST is slow. Two independent mechanisms then restore the colour, and only the first needs a race:

- Server ordering. `forget` DELETEs and, if the DELETE reaches the handler before the stalled POST, the POST re-creates A as hand-set *after* the release. `forget` returns true, `_resetColours` reports nothing, and the next `load()` pulls `sky/true` back into the cache. FACT for the store (above); SUSPICION only on the arrival order - and it is the slow POST that put the user in this window in the first place.
- Re-capture, no race needed. FACT by trace. In this window the capture pass has not painted yet, so `releaseMenuColour` was never called and the companion's localStorage record is intact. `_resetColours` calls `reconcileColours()` at `panel.ts:950`; that pass reads `readUserSetTabColour` as `'sky'` (`terminals.ts:318-320`), finds `held` false because the cache was just cleared (`:334-338`), and re-issues `set(A,'sky')` at `:340`. The reset is undone by the reset's own refresh.

The docstring at `panel.ts:934-938` names the adjacent case (tab closed inside the capture window) but not this one, where the tab stays open and the reset lands inside it. Fix: `_resettableColours` must not offer an id with an unanswered write - filter it with `isPending` at `panel.ts:2017` (a colour that is still being stored is not yet the user's to take back), or serialise writes per id so `forget` queues behind the capture rather than racing it. The second also closes the general class this is one instance of: the cache follows issue order, the server follows arrival order, and nothing reconciles them.

## Tested and cleared

- **`_writeStart` unbounded growth - not a leak.** It is a `Map` keyed by conversation id, so it is bounded by the number of distinct ids ever written (each of which also holds a `_colours` entry), and any successful `load()` prunes every id that has caught up (`colour.ts:205-213`). A server that is down grows it by nothing, since writes fail but ids repeat.
- **`_writeStart` pruned while still needed - yes, and that is NEW-1.** The prune is correct with respect to writes and wrong with respect to a second, older read; there is no read counter.
- **`_branchCache` serving one project's list under another's row - cannot happen.** It is keyed on `session.encoded_path` (`panel.ts:1965`, `:1994`), which `types.ts:101-103` defines as the provider's own project key, one per row; the panel instance is per provider, so two providers cannot collide either. Every staleness path I found (NEW-3 included) is same-project.
- **`_snapshot`'s currency check against `forget`'s multi-id write.** Per id, not per set - `t4_partial_overtake.js` above; the overtaken id keeps the newer value and the rest roll back, cache and server identical.
- **The strip path does not destroy the user's colour.** `_applyColour(widget, null)` reaches `setColour(widget, null)`, and `releaseMenuColour` is gated on a truthy `colourId` (`jupyterlab_colourful_tab_extension/src/index.ts:454-461`), so the companion's record survives and `refreshAllTabColours` repaints it. The `terminals.ts:342-352` early return is safe.
- **`_openContextMenu` cannot leave an unhandled rejection.** `branches()` catches at `:1967`, `load()` catches internally (`colour.ts:179-181`), `reconcileColours` now catches at `terminals.ts:371`, so neither leg of the `Promise.all` at `:1983` can reject after the timeout has already won the race.
- **`_colouredTabs` on the panel.** Now assigned at `panel.ts:248`, defaulted true at `:2145`, and pushed on every settings load, so `isVisible` at `:1766` is not gated behind a signal that never fires.
