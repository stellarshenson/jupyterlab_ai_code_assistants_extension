## Verdict

`VERDICT: DO-NOT-SHIP (8 findings)` - worst: Gemini's terminal identity is hardcoded to one Node release's thread name and is dead on every Node version the Gemini CLI actually supports.

## Findings

**1. [MAJOR] Gemini is unidentifiable in a terminal on Node 20-25 - the `comm` gate is Node-version specific** - `jupyterlab_ai_code_assistants_extension/providers/gemini.py:412` (`comm_name = "node-MainThread"`), consumed via `core/store.py:351` from `core/routes.py:139`.

FACT, runtime-proven. `/proc/<pid>/comm` for a Node main thread is **`MainThread`** on Node 24.19 and **`node-MainThread`** on Node 26.6:

```
node24 comm= 'MainThread'      owns_pid= False
node26 comm= 'node-MainThread' owns_pid= True
```

(probe ran the real bundle path `/home/lab/.local/lib/node_modules/@google/gemini-cli/bundle/gemini.js` as argv, so only the comm differed). The installed `@google/gemini-cli` 0.54.4 declares `engines: {node: ">=20"}`, and `#!/usr/bin/env node` resolves under the **Jupyter server's** PATH, not the author's shell.

Failure scenario: server PATH resolves Node 20/22/24 → `GeminiStore.owns_pid` returns False at the first line → `_tree_assistant` returns `(None, None)` → `GET providers/gemini/terminal/<name>` answers `running: false, session_id: null` → (a) `TerminalManager.findForSession` never matches, so after any page reload a click on a Gemini row that already has a terminal open spawns a **second** terminal on the same conversation, unbounded; (b) `_eachAssistantTerminal` skips the widget (`!info.running`), so Gemini tabs are never tinted and a hand-set tab colour is never captured. Silent - nothing logs.

The test suite cannot catch it: `tests/test_provider_stores.py:639` monkeypatches `process_comm` to return the literal `"node-MainThread"`, baking in the assumption under test.

Fix: accept the set `{"node", "MainThread", "node-MainThread"}`, or drop the comm pre-gate for this store entirely - the argv element check at `gemini.py:858-861` is already the authoritative discriminator (that is what DEF-24 established), and the comm check now only fails closed.

**2. [MAJOR] Every destructive route runs its store work inline on the IOLoop** - `core/routes.py:327` (`def delete`, not `async def`) and `:399` (`def post` on switch), against the async+executor treatment the same class gives `GET` at `:305-313`.

FACT. `SessionsHandler.delete` calls `provider.store.remove` / `delete_branches` directly on the event loop. For Codex those are one `subprocess.run` **per conversation** (`providers/codex.py:592-623`, `_CLI_TIMEOUT_S = 30` at `:79`). Measured on this machine: `codex archive <id>` = **0.71 s** per call (`codex --version` alone = 0.094 s), so the docstring's "~70 ms" is off by ~10x.

Failure scenario: user right-clicks a Codex project holding 20 conversations → "Clean Up Parallel Sessions" → 20 sequential CLI spawns on the IOLoop → **~14 s during which the entire Jupyter server is frozen** for every user and every kernel: no kernel output, no terminal I/O, no notebook saves, no other panel's poll. A codex binary that hangs (network-bound app-server call) makes the ceiling `30 s × N`. The same handler runs `send2trash` for the other three providers, which copies across devices on a cross-filesystem trash.

`SwitchHandler.post` has the same shape at lower cost (Codex's `switch` runs a full `list_threads`, which degrades to an `rglob` over `~/.codex/sessions/**/rollout-*.jsonl` reading 10 lines of every file when the sqlite index is unreadable).

Fix: `async def` + `run_in_executor` for `SessionsHandler.delete` and `SwitchHandler.post`, exactly as `get` already does.

**3. [MAJOR] One malformed number in the assistants' own JSON kills the whole Claude listing, permanently** - `providers/claude.py:348-360` and `:650`.

FACT, reproduced twice against a scratch `CLAUDE_CONFIG_DIR`:

```
claude.py:360  fresh = (now_ms - updated_at) <= REMOTE_CONTROL_FRESH_MS
TypeError: unsupported operand type(s) for -: 'int' and 'str'

claude.py:650  latest["fileMtime"] = max(int(latest.get("fileMtime") or 0), fs_mtime)
ValueError: invalid literal for int() with base 10: '2026-01-01T00:00:00Z'
```

Every neighbouring field in `_session_state_by_cwd` is type-checked (`cwd`, `pid`, `name`, `bridgeSessionId`); `updatedAt`/`startedAt` alone is used raw in both a comparison (`:350`) and arithmetic (`:360`).

Failure scenario: one `~/.claude/sessions/<pid>.json` carrying an ISO-string `updatedAt` (Claude never prunes that directory, so any file a future or older CLI version wrote lives forever), or one `sessions-index.json` entry whose `fileMtime` is not an int → `list_sessions` raises out of the executor → 500 on the sessions poll → the panel shows "Could not reach the server - retrying" for **all** projects, on every 30 s tick, forever, with nothing naming the offending file. Compare DEF-15, which fixed exactly this blast radius for the stat race and left the numeric fields unguarded.

Fix: `isinstance(..., (int, float))` gates on `updated_at` before the compare and the subtraction, and swap `int(x or 0)` for a guarded coercion.

**4. [MINOR] "Atomic" state writes share one temp filename and are unguarded read-modify-writes** - `core/store.py:71-84` (`tmp = path.with_suffix(path.suffix + ".tmp")` - a fixed name per state file), used by `core/state.py:85-96,123-137,140-154`, `core/migrate.py:114,122` and `core/colour_store.py`.

FACT, measured. Three processes writing one provider's state (`JUPYTERLAB_AI_CODE_ASSISTANTS_STATE_DIR` shared):

```
exceptions: 297 of 900  FileNotFoundError: '.../claude.json.tmp' -> '.../claude.json'
favourites kept: 399 of 900
concurrent reads that came back EMPTY (file unparseable): 9 of 600
```

Both processes open the *same* tmp path with `"w"`, so they share one inode; the loser's buffered write lands inside the file the winner has already renamed into place, and its own `os.replace` then raises.

Failure scenario: two Jupyter servers under one `JUPYTER_DATA_DIR` (the default `~/.local/share/jupyter`). Starring a project in one → 500 out of `FavouriteHandler` (`toggle_favourite` does not catch `OSError`) and "Could not toggle favourite". Worse, a sessions poll landing in the corrupt window reads `load_state` as empty (`state.py:47-67` degrades silently) → every **pin** disappears for that poll → the row resolves by recency to a different conversation → the click resumes the conversation the user switched away from, which is the exact failure the pin exists to prevent. Not rated higher because it needs a second server and nothing is destroyed permanently.

Fix: unique temp name (`mkstemp` in the same directory, or `.tmp.<pid>`), and treat `save_state` failures in `toggle_favourite` the way `write_pin` already does.

**5. [MINOR] Every Codex branch ends with a warning toast stating a reason that is not Codex's** - `src/core/panel.ts:1072-1077` against `providers/codex.py:529-548`.

FACT for the mechanism, verified with a synthetic thread list:

```
switch to the freshly forked thread -> {'requested': '2222...', 'current': '1111...'}
```

Codex's `switch` resolves `current` over the **visible** population, and a thread with no turn yet (`has_user_event` false, empty preview) is not in it - the store's own docstring says the disagreement is deliberate, and `list_branches` exists specifically so "the fork watcher must see a new thread before its first turn lands". `_watchForNewBranch` (`panel.ts:1041`) calls `_switchBranch` the moment it discovers that turn-less fork, and the frontend prints Claude's cwd rule verbatim: *"That conversation cannot become current - its recorded folder does not match the project."* Codex has no such rule; the fork is fine and is pinned. SUSPICION only on whether `codex fork` ever arrives already carrying a preview - settling test: fork a real Codex thread and read `has_user_event`/`preview` from `state_5.sqlite` before the first turn.

Fix: make the copy provider-neutral ("that conversation is not the project's current one yet"), or suppress the warning on the fork-discovery path.

**6. [MINOR] The init waiter burns its full 5 s fallback when the client attaches at exactly 24x80** - `core/routes.py:44-55`.

FACT, measured through a real pty with the production argv:

```
default pty size: 24 80
no client resize:      5.16 s
resize to 40x120:      0.31 s
resize to SAME 24x80:  5.15 s
```

The comment's strategy ("loop until either SIGWINCH fires OR the size has visibly changed") assumes a resize to the same dimensions still signals; Linux `tty_do_resize` returns early without raising SIGWINCH when the new winsize equals the old, and ptyprocess spawns at 24x80. A browser terminal that happens to render 24 rows x 80 columns therefore waits the whole timeout before the assistant appears - it looks like a hung launch behind the modal spinner.

Fix: spawn the pty at a size no client will land on (e.g. 1x1 via `dimensions` in `term_settings`), so any client resize is a genuine change.

**7. [MINOR] Serving Jupyter at `/` silently disables New Session, Open Terminal and Show in File Browser** - `src/core/panel.ts:157` (`this._rootDir = (options.rootDir || '').replace(/\/+$/, '')`), `:746-749`, `:752-757`, `:1538-1549`.

Traced, not run. `root_dir` of `/` normalises to the empty string. Then: `_currentFolder()` returns `''` at the browser root → `_newSession` hits `if (!projectPath) return;` and the `+` button does nothing at all - no launch, no error, no toast. `_pathUnderRoot` returns `null` unconditionally (`if (!this._rootDir) return null`), so "Open Terminal" and "Show in File Browser" answer *"Folder is outside the JupyterLab root"* for every row, including rows inside it.

Failure scenario: a container image started with `--ServerApp.root_dir=/`. Fix: keep `/` as `/` (strip trailing slashes only when the result is non-empty) and special-case it in `_currentFolder`/`_pathUnderRoot`.

**8. [MINOR] One rejecting settings key drops the remaining providers' migrated settings, and the marker blocks the retry** - `src/index.ts:296-302` against `core/migrate.py:116-123`.

Traced. The server adds **every** provider to the marker set and writes it before returning (`migrate.py:116,122`); the frontend then applies the returned keys in a bare `for … await settings.set(key, value)` inside one `try`. A single rejection - a settings PUT that fails, a legacy value whose type the schema refuses - aborts the loop, is swallowed as a `console.warn`, and the marker means no later activation ever offers those keys again. This is the residual of DEF-13, which closed only the `settingRegistry` unavailable case. SUSPICION on how easily `set` rejects for these three boolean keys; settling test: make the config dir read-only and run a first activation with legacy settings present.

Fix: per-key `try/catch`, and have `POST migrate` mark a provider only after the frontend confirms (or return the keys without marking until a follow-up call).
