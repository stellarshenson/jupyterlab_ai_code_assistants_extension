## Findings

1. **[MINOR] The row tooltip promises a launch mode the server discards on a background-agent row** - src/core/panel.ts:1612, against jupyterlab_ai_code_assistants_extension/providers/claude.py:985-986. FACT (runtime + server source).
   `_buildRowTooltip(s)` reads `this._resolvedVariant()`, which since the DEF-37 fix no longer consults `bg_id` at all, and appends `Launch mode: <label>`. Its own comment one line down says "The row click launches with this". For a Claude row holding a live background agent that is false: a row click runs `_openSession(session)` -> POST with `mode: dangerouslySkipPermissions` -> `ClaudeStore.launch_argv` resolves `attach_id` and returns `[claude, attach, <id>]` at line 986, BEFORE the `--dangerously-skip-permissions` append at 987-988. The flag is dropped by design ("attach takes no options").
   Failure scenario: settings have Dangerously skip permissions on; a project's current conversation is held by a live background agent. Hover that row -> tooltip reads `Background agent: agent-7 (click attaches to it)` AND `Launch mode: Skip Permissions`. Right-click the same row -> the menu's first item reads `Attach to Background Agent` with no suffix and no triangle, because it goes through `_resumeVariant()` (panel.ts:1764). Two surfaces on one row, one sentence apart, disagreeing about whether a permission bypass applies. Proven at runtime: my spec printed `"bg\nPath: bg\nBackground agent: agent-7 (click attaches to it)\nLaunch mode: Skip Permissions\nSession id: b1"`.
   This is new. It is the mirror of DEF-37: that defect was `_resolvedVariant` testing bg for callers that never attach; the fix removed the test from all of them, including the one caller that DOES describe an attach.
   Fix: the tooltip describes a specific ROW, so it must test that row, not `_activeSession`. Give `_buildRowTooltip` its own resolution - `const variant = this._descriptor.hasBgAgents && s.bg_id ? null : this._resolvedVariant();` - rather than reusing either of the two panel-scoped helpers. Note `_resumeVariant()` cannot be reused here: it reads `_activeSession`, and the tooltip is built for every row on every render.

2. **[MINOR] The init waiter still has a ~2 ms inversion window, and its worst case is a 5.5 s stall followed by a 1x1 assistant** - jupyterlab_ai_code_assistants_extension/core/routes.py:53-62. FACT (measured, table above).
   The sentinel is now absolute and child-owned, which removes the interleaving your sweep tested. What it does not remove is the case where the client's resize lands BEFORE the child reaches `stty rows 1 cols 1`: the pty is set to the browser's size, the child then stamps 1x1 over it, and nothing resizes it again - `resize_to_smallest` only runs on a new `set_size` message, and @jupyterlab/terminal only emits one on an actual widget resize (lib/widget.js:435-462, `_resizeTerminal` -> `_setSessionSize`, driven by `_needsResize` from `onResize`). The child then burns all 50 iterations and execs at 1x1.
   Measured: bad 10/10 at 0 ms, 9/10 at 1 ms, 1/10 at 2 ms, 0/10 from 3 ms. The child's `stty` completes ~2 ms after `PtyWithClients.spawn` returns.
   Failure scenario: the browser's first `set_size` beats a slow bash start (cold page cache for /bin/bash, a loaded box, or a stale terminal widget reconnecting to a name terminado has just reused). The user sees a blank terminal for 5.5 s, then an assistant rendering into one column, until they resize the window or drag a sidebar.
   Same wrong end-state is reached with no race at all whenever no client ever attaches: measured `falls back at 5.50s, size=('1','1')` - the child execs the assistant into a 1x1 window on purpose. That is the documented fallback, and it is the wrong size to fall back to.
   Fix (one command, closes both): make the timeout path restore a sane geometry instead of shipping the sentinel into the assistant - `for i in ...; do ...; sleep 0.1; done; [ "$(stty size 2>/dev/null)" = "1 1" ] && stty rows 24 cols 80 2>/dev/null; clear; exec "$@"`. The success path is untouched; the two failure paths become a 24x80 assistant that the first real resize corrects, instead of a 1x1 one.
   SUSPICION, and I could not settle it: whether the 0-2 ms inversion is reachable through a real browser at all. The client's resize cannot precede the launch POST's response, so it carries an HTTP round trip the child does not. Settling test: instrument `TermSocket.on_message` for `set_size` and `PtyWithClients.__init__` with monotonic timestamps in a live JupyterLab, launch 200 terminals from the panel, and record the distribution of (first set_size) - (spawn return). The fix above is worth taking regardless, because the no-client case needs it and costs nothing.
