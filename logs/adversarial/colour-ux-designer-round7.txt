## Direct answers

**Is 800 ms with a kept-fetch fallback acceptable?** The ceiling: yes, unreservedly. I re-measured `claude agents --json` at 320/338/343/309/311/318 ms, so 800 ms is 2.3-2.6x the honest work and lands inside the ~1 s flow-of-thought window; the retry amplification I filed is bounded to ~1.6 s worst case instead of ~3 s. The retention: right in principle, wrong in reach. A degraded-then-complete menu is strictly better than a silence, because *missing* items are legible (reopen and they appear) - but the cache as built produces *wrong* items, which are not, and it does so on a path that has nothing to do with losing a race. That is a worse confusion than the wait it replaced, and it is finding NEW-F below.

**Does the rewritten README bullet say only true things?** No - caveat 1 is false (NEW-G). The other new clauses check out. **Is it still readable at that length?** No: 150 words against 12-43 for every one of the 17 other feature bullets (NEW-H).

**Anything left a user would experience as unexplained?** Two: the phantom conversations (NEW-F), and a colour picked on a brand-new Codex/Kimi tab silently vanishing when the conversation is reopened, with the README pointing at that exact gesture as the remedy (NEW-G).

## (b) New friction

- **[MAJOR] NEW-F - the kept fetch is consulted where nothing was ever fetched, so a cleaned-up project's menu lists conversations that no longer exist, permanently.** `panel.ts:1955-1957` returns `null` *without fetching* when `session.extra_sessions <= 0`; `:1992-1996` cannot tell that null from a lost race and falls back to `_branchCache`, which is written only at `:1965` and cleared nowhere (`_branchCache` occurs at `:1965`, `:1994`, `:1995`, `:2152` and nothing else). `_deleteBranches` (`:1108-1114`) and `_cleanupParallel` (`:620`) both leave it. Walk it: right-click a project with 4 conversations (cache filled) → `Clean Up Parallel Sessions`, which by definition drives `extra_sessions` to 0 → right-click the same row again. The fetch is skipped, the stale cache wins, `:2000-2002` overwrites `_lastBranches` with the deleted list and refills both submenus, and `_rebuildContextMenu(true)` shows `Switch and Manage Sessions (4)` / `Open Branched Conversation (4)` for a project that now has one conversation - while the same row's branch icon is gone (`:1364`) and `Clean Up Parallel Sessions` has hidden itself (`:1773`), so the menu contradicts the row it was opened from. Clicking a phantom gets `'That conversation no longer exists - the list has been refreshed.'` (`:1076`) - a sentence that is false here, since nothing refreshes the cache; the next right-click offers the same phantoms. It self-heals only if another project with live branches wins the single cache slot. `Manage Sessions...` inherits it too: the popup renders `_lastBranches` on open and only calls `onRefetch` after a delete (`/home/lab/workspace/private/jupyterlab/jupyterlab_ai_code_assistants_extension/src/core/popup.ts:405-417`). Fix, one condition: fall back to `_branchCache` only when a fetch was actually attempted - gate `:1992-1996` on `session.extra_sessions > 0`. (Clearing the cache in the delete and cleanup paths also works but is two edits and still misses a delete made from another browser tab.)
- **[MAJOR] NEW-G - the new caveat prescribes a remedy that does not restore the colour; the user watches it vanish at the moment the README says it is remembered.** `README.md:37`: "a colour set on a Codex or Kimi conversation that has never been resumed is remembered only once you reopen that conversation from the panel", and `docs/acc-crit-jupyterlab-ai-code-assistants.md:256` says the same ("is not captured until it is reopened from the panel"). Traced end to end, reopening captures nothing. The colour lives only in the companion's storage under `terminal:<session name>` (`/home/lab/workspace/private/jupyterlab/jupyterlab_ai_code_assistants_extension/src/core/colour.ts:56,63`). Reopening from the panel cannot reuse the original terminal - the microcache needs `cached.sessionId === wanted` (`/home/lab/workspace/private/jupyterlab/jupyterlab_ai_code_assistants_extension/src/core/terminals.ts:120`) and a bare Codex/Kimi launch tags it `undefined` (`panel.ts:758,773`, `mintsNewSessionId: false` at `src/providers/codex.ts:54` and `src/providers/kimi.ts:131`), and `findForSession` (`terminals.ts:213-226`) matches on an id the original process does not carry (`providers/codex.py:697-705`, `providers/kimi.py:684-690`). So it falls to `launch`, which calls `terminal_manager.create(...)` (`jupyterlab_ai_code_assistants_extension/core/routes.py:715-725`) - a NEW terminal with a new name, so `readUserSetTabColour(newName)` returns null and no capture runs. Meanwhile the original tab's entry is deleted the moment its terminal closes (`/home/lab/workspace/private/jupyterlab/jupyterlab_colourful_tab_extension/src/identity.ts:52-60`, `deadTerminalIds`). Net user experience: pick a colour, it sits on the tab for the whole session, reopen the conversation as the README instructs, and the tab comes back with the assistant's default and no explanation - the one place the docs promised it would be remembered. Fix, say what happens: "a colour set on a Codex or Kimi conversation that has never been resumed is not remembered - reopen that conversation from the panel and set the colour again on the new tab, which is remembered." Same correction at acc-crit `:256`.
