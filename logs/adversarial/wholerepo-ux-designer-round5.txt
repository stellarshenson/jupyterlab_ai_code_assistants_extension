FINDING 1 - CRITICAL - FACT
Irreversible confirmations put the keyboard on the destructive button
src/core/panel.ts:635-642 (Remove from <assistant>), :674-682 (Clean Up
Parallel Sessions)
--------------------------------------------------------------------------------
Both dialogs are raised as

    showDialog({ title, body, buttons: [Dialog.cancelButton(),
                                        Dialog.warnButton({label: 'Remove'})] })

with no `defaultButton`. JupyterLab's `showDialog` normalises the missing field
to `buttons.length - 1` (apputils/lib/dialog.js:790), `_primary` is set from
that index (:111), and `onAfterAttach` calls `this._primary.focus()` (:248). The
destructive button therefore owns the keyboard the instant the dialog appears.
Enter or Space commits. `Dialog.resolve()` with no index also falls back to
`_defaultButton` (:175), so an Enter that lands while nothing is focused commits
too.

The body of the Remove dialog reads "This drops the entire project history and
every conversation it holds ... This cannot be undone." That sentence is
addressed to a user whose finger is already on the button that does it.

Executed (scratch copy, jsdom):
    ✓ focuses the LAST button when defaultButton is omitted (panel.ts pattern)
        -> document.activeElement.textContent === 'Remove'
    ✓ focuses Cancel when defaultButton: 0 (JupyterLab file-browser pattern)
        -> document.activeElement.textContent === 'Cancel'

JupyterLab's own file browser already made this call, in the opposite
direction, with the reason written down - node_modules/@jupyterlab/filebrowser/
lib/listing.js:433-436:

    // By default focus on "Cancel" to protect from accidental deletion
    // ("delete" and "Enter" are next to each other on many keyboards).
    defaultButton: 0

This extension's Remove sits in a context menu whose neighbours are Copy Path
and Show in File Browser, and the menu is reachable by Shift+F10 from a
keyboard-navigated row (panel.ts:1543) - i.e. the whole path from "browsing
rows" to "history destroyed" can be walked without a mouse, and its last step
is the default action.

Fix is one line per site: `defaultButton: 0`.

Note the internal inconsistency this creates. The Manage Sessions popup takes
the danger of the same operation seriously enough to build a bespoke two-step
arm/confirm in its footer (popup.ts:385-404) with a 4-second disarm, because
permanent deletion "cannot be taken back". Two surfaces, same data, opposite
postures.

FINDING 2 - MAJOR - FACT
A failed launch erases its own error message before it can be read
src/core/panel.ts:788-792 (_openSession), :831-835 (_newSession),
against :598 (_fetch)
--------------------------------------------------------------------------------
`_openSession` and `_newSession` both do:

    catch (err) { ... this._showError(err); }
    finally     { void this._fetch().catch(() => undefined); }

and `_fetch` opens with `this._setInlineError(null)` on success (:598). So the
inline strip is painted in the catch and wiped one round trip later by the
finally. For every non-404 failure - the launch route 500s, the terminal cannot
be created, `terminal:open` rejects - the user's only feedback is an error strip
that exists for the duration of one GET.

Executed (scratch copy, jsdom, real AssistantSessionsPanel with `requestProvider`
stubbed to resolve `{sessions: []}`):
    after failure  -> hidden= false | text= "Could not reach the server -
                      retrying. launch refused by server"
    after _fetch() -> hidden= true  | text= ""
    (and the same for the `_showActionError` copy)

The 404 branch is fine - it uses `Notification.error` (:781), which survives.
Everything else is the flash.

The codebase already knows this. `_resetColours` (:994-1004) carries the comment:

    // No refresh afterwards: `_fetch` clears the inline error, and a failure
    // the user never sees reads as a reset that silently did nothing.

The rule was written for the colour reset and not applied to the two paths that
matter most - the row click and the `+` button, which are the panel's entire
primary interaction. Clicking a session and having nothing happen, with no
residue, is the worst possible failure shape for a launcher.

Secondary, same mechanism, lower stakes: `_toggleFavourite` (:625) and
`_removeProject` (:664) write `_showActionError` and do NOT refresh, so their
message survives - until the 30-second background poll's `_fetch` wipes it
(:598). A one-shot error with a 30-second self-destruct is better than 200 ms
but still not a message the user dismissed.

Fix: give the inline strip a "sticky until the user acts" flag, or route
one-shot action failures to `Notification.error` the way the 404 already does.

FINDING 3 - MAJOR - FACT
The one-click, no-menu, approval-bypassing launch is the only launch surface
with no warning glyph
src/core/panel.ts:302-342 (the `+` button) vs :1791-1793, :2035, :1820, :2015
--------------------------------------------------------------------------------
When a boolean skip-approval mode is on in settings, `_buildsSameLaunch` is true
for it, `_visibleVariantCount()` returns 0, and the `+` button changes character:
it stops dropping a menu and launches directly on click (:334-337).

That is exactly the configuration in which the launch bypasses every approval
prompt. Claude's mode is `dangerouslySkipPermissions` -> `--dangerously-skip-
permissions`; Codex's is `--dangerously-bypass-approvals-and-sandbox`; Kimi's is
`--yolo`. `resolvedLaunchModeEntry` marks all three `unsafe: true` (modes.ts:83-85
- a boolean mode carrying a `menuLabel` IS the skip-approval switch).

Every OTHER surface marks that with the caution triangle:
    new-session command      icon: () => this._variantIcon()        (:2035)
    resume command           icon: () => ...unsafe ? warningIcon    (:1820)
    branch-session command   icon: () => this._variantIcon() ?? ... (:2015)
    every forced variant     icon: warningIcon                      (:1832,1849,1855)

The `+` button gets `addIcon.element({container: newBtn})` (:330) unconditionally
and nothing else. Its only cue is the `title`, which DEF-36/38 correctly fixed -
but a tooltip is a hover-or-focus disclosure on a 24px icon button, and the
click it guards needs no hover and opens no menu. The safest-looking control in
the header is the one that fires the unguarded launch, in one click, with no
intermediate menu to show the triangle the design language reserves for it.

The panel's own reasoning agrees with me, in `_resolvedVariant`'s docstring
(:1737-1743): marking only the forced variant "puts the warning on the SAFER-
looking of two entries ... and the unmarked one is the default the user clicks."
That is the argument for finding 3, applied one surface further out.

Fix is small: swap the glyph, or add a modifier class on the button, when
`_variantIcon()` is defined - and re-run it from `_renameNewButton`, which
already re-runs from `setModes`.

FINDING 4 - MAJOR - SUSPICION (structure verified; consequence not renderable)
The cleanup progress modal hides its only exit, so a stalled request has no
keyboard way out
src/core/panel.ts:703-717, :753-757
--------------------------------------------------------------------------------
`_cleanupParallel` launches a second Dialog whose only button is
`Dialog.okButton({label: 'Close'})`, then immediately does:

    const footer = dialog.node.querySelector('.jp-Dialog-footer');
    if (footer) { footer.style.display = 'none'; }
    void dialog.launch();

and restores it in `finally`. Between those two points the dialog is an app-wide
scrim containing a message, a `<progress>`, and one control that is not rendered.

What I executed (scratch copy, jsdom):
    buttons in dialog: [ 'Close|footerHidden=none' ]
    focusable count:   1
i.e. the single focusable control is confirmed to sit inside the footer whose
`display` is `none`.

What I could NOT execute, and why it is a SUSPICION not a FACT: jsdom does no
layout, so `HTMLElement.focus()` on a `display:none` descendant SUCCEEDS there -
my probe saw activeElement land on the hidden Close button, which a browser will
not do (a non-rendered element is not a focusable area). In a real browser the
`_primary.focus()` at dialog.js:248 is a no-op, focus stays on whatever the user
had (a panel row, outside `dialog.node`), and Dialog's Escape handler is
registered on `node` only (dialog.js:230) - so an Escape keydown targeted at the
row never traverses the dialog node and never reaches the handler. Verifying that
needs Galata, which this round forbids.

If it reproduces, the cost is: a hung DELETE (and `requestAPI` sets no timeout -
the panel's own `_openContextMenu` comment at :2199-2202 makes exactly this
point) leaves the user in an undismissable modal with a reload as the only exit.

The strongest evidence that this is real is 200 lines away in the same repo.
`showLaunchSpinner` (terminals.ts:44-52) keeps its button visible on purpose:

    // `Hide`, not `Cancel`. The button takes the scrim away and nothing else
    ...
    // so a stalled launch cannot leave the user staring at a modal with no exit.

Two progress modals, one rule, applied to one of them.

FINDING 5 - MINOR - FACT
The filter toggle communicates its state to sighted users only
src/core/panel.ts:344-350, :440-457
--------------------------------------------------------------------------------
`filterBtn` is a toggle: `_toggleFilterBar` flips `searchWrap.hidden` and calls
`this._filterBtn.classList.toggle('jp-mod-active', show)`. The class drives a
background and a brand-coloured glyph (base.css:69-72). Nothing else changes.

`grep -rn "aria-" src/ --include=*.ts` returns 16 hits and not one is on this
button: no `aria-pressed`, no `aria-expanded`, no `aria-controls`. Its title
stays the literal string 'Filter sessions' in both states (:346, written once).
So to a screen-reader user the button is a plain "Filter sessions" push button
whose pressed state, and whose ownership of the field that appears and
disappears, are invisible.

This is out of step with the same file's own standard: `_renderSection` puts
`aria-expanded` on the section header and marks the caret `aria-hidden` because
"the state it draws is already on the header's aria-expanded" (:1381-1387). The
filter button is the same widget shape and got neither.

Note the second-order effect: toggling the bar OFF also silently clears an
active filter (:451-455). A user who cannot perceive the toggle state cannot
perceive that their query was discarded either.

Fix: `aria-pressed` mirroring `show`, plus `aria-controls` pointing at the
wrapper (give it an id).

FINDING 6 - MINOR - FACT
Every row is a tab stop, and one project can be three of them
src/core/panel.ts:1433-1437, :1319-1336
--------------------------------------------------------------------------------
`_renderRow` sets `role="button"` and `row.tabIndex = 0` on every row, and
`_render` renders the same project into Favorites, Recent and All (:1332-1336) -
the panel's comment at :1288-1290 acknowledges the triplication when restoring
focus. So a favourited project occupies three sequential tab stops, and the
`all` section is uncapped: with 60 projects and 10 favourites the panel is ~80
tab stops plus 3 headers before Tab leaves it for the rest of the sidebar.

There is no arrow-key navigation and no roving tabindex - `keydown` handles only
Enter, Space, ContextMenu and Shift+F10 (:1531-1550). The ARIA authoring
practice for a list of same-kind items is one tab stop into the list and arrow
keys within it; this is the opposite.

Not a blocker on its own, and cheap to defer - but it is the friction ceiling on
every keyboard workflow in the panel, and it compounds DEF-44 (Recent and All
rendering the identical list below the recent limit), which doubles the stops
for the common small-workspace case.

CONSIDERED AND DISMISSED (so the next round does not re-litigate them)
--------------------------------------------------------------------------------
* "Delete moves to trash (recoverable)" in the popup (popup.ts:118-120) is an
  HONEST claim. `core/store.py:203-221` routes through `send2trash` when
  `to_trash`, and RAISES rather than falling back to a permanent delete, with the
  reason written down. Checked because a false recoverability promise would also
  invalidate `armsFirst`. It is true.
* Missing `:focus-visible` styles. base.css defines focus styling only for the
  two search inputs, but nothing in this extension or in JupyterLab's global CSS
  sets `outline: none` on buttons or on `[tabindex]` (the ui-components resets at
  base.css:141 and :213 are scoped to `.jp-InputGroup` / `.jp-HTMLSelect`), so
  the UA ring survives. No finding.
* The green status dot is used for two different states (remote control vs live
  process, panel.ts:1561-1572) with identical class and colour. No shipped
  provider sets both `hasRemoteControl` and `hasLiveProcess`, so the two never
  appear in one panel. Not a defect today; a trap for provider number five.
* Duplicate "No matches." across sections under a filter. Cosmetic, and DEF-44
  already owns the Recent/All duplication ground.

--------------------------------------------------------------------------------
VERDICT
--------------------------------------------------------------------------------
DO-NOT-SHIP.

Finding 1 alone is the bar: an irreversible, explicitly "cannot be undone"
operation whose confirmation dialog hands the keyboard to the destructive
button, in a codebase whose own dependency shipped the one-line fix with a
comment explaining why. Finding 2 removes the feedback from the panel's primary
interaction. Finding 3 leaves the fastest approval-bypassing launch as the only
one the design language does not mark.

1, 2, 3 and 5 are each a small, local, low-risk change. None of them needs a
browser to fix, and 1, 2 and 5 do not need one to verify either.
