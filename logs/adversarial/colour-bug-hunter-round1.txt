## Verdict
`VERDICT: DO-NOT-SHIP (7 findings)` - the newly-enabled write-back files a hand-set Claude colour against whatever conversation the cwd fallback guessed, so colouring one tab recolours a different conversation.

## Findings

**1. [MAJOR] Write-back persists a guessed conversation id, not an observed one** - `src/core/terminals.ts:303-318`.
`sessionId` is `info.session_id ?? sessionForCwds(info.cwds, this._sessions)?.session_id`. That fallback is documented in `src/core/colour.ts:95-99` as a *read* fallback (the project's representative conversation, not this terminal's). The change now feeds it straight into `this._colours.set(sessionId, userSet)` - a write of identity based on a guess.

Failure scenario (FACT, traced): project `/p` has conversations A (row representative) and B. User opens a Claude terminal on B; `session_id_for_pid` returns None because `_expand_short_session_id`/`_session_id_from_pidfile`/`parse_session_id` all miss before Claude's first turn writes `sessions/<pid>.json` (`jupyterlab_ai_code_assistants_extension/providers/claude.py:1011-1022`). Probe returns `running: true, session_id: null, cwds: ["/p"]`. `sessionForCwds` resolves A. User right-clicks the tab → `mint`. Next pass writes `store[A] = 'mint'`, then `_applyColour` → `setColour(widget,'mint')` → `releaseMenuColour` deletes the localStorage entry (`node_modules/jupyterlab_colourful_tab_extension/lib/index.js:160-172, 384-392`). Result: conversation **A** turns mint - its row swatch and its own terminal - while B's record of the user's choice no longer exists anywhere.

Worse sub-case: if `store[A]` already equals `'mint'`, the `userSet !== this._colours.get(sessionId)` guard skips the write entirely, `_applyColour` still releases the menu entry, and the choice on B is destroyed outright - exactly the loss the new guard at `terminals.ts:320-326` was added to prevent.

Fix: write back only on a POSITIVELY observed id. Keep `info.session_id` for the write, keep the cwd fallback for the read:
```
const observedId = info.session_id ?? null;
const sessionId = observedId ?? sessionForCwds(...)?.session_id ?? null;
if (observedId && userSet && userSet !== this._colours.get(observedId)) { ... }
if (userSet && !observedId) { return; }   // guard moves to the observed id too
```

**2. [MAJOR] A failed store POST silently destroys the colour within one poll** - `src/core/colour.ts:143-161` + `165-187`, `src/core/terminals.ts:316-342`.
`set()` updates the in-memory cache, then swallows a failed POST ("the cache already reflects the intent; the next load reconciles" - `colour.ts:185`). But `load()` does not reconcile, it **replaces**: `this._colours = next` (`colour.ts:157`). By then `_applyColour` has already made the companion extension delete the localStorage entry.

Failure scenario (FACT, traced): user sets `mint`; reconcile writes cache + POSTs; the POST 500s (state dir unwritable - `colour_store.py:49-52` swallows `OSError` server-side and still answers 200, so the more likely trigger is a network blip or a restarting server). Tab is painted mint, menu entry released. ≤30 s later `panel.ts:539` runs `load()` → succeeds → cache replaced by the server's map, which has no entry → `reconcileColours` finds no `userSet` (released) and no store entry → repaints the native/derived/none default. The user's colour is gone with no reload and no error. Requirement 2 says this must never happen.

Fix: track un-acked writes and re-apply them over the loaded map, or `await` the POST and skip `_applyColour` for that widget when it rejects (leaving the menu entry intact for the next pass to retry).

**3. [MAJOR] The override is a one-way door in the UI - and the new spec asserts otherwise** - `src/core/terminals.ts:313-318`, `ui-tests/tests/colour-override.spec.ts:74-98`.
The only frontend write is `set(sessionId, userSet)` with truthy `userSet`; the only deletions are `forget()` on conversation deletion (`panel.ts:674, 1069`). The companion's "Clear" command deletes the localStorage entry and strips the DOM classes but never touches `widget.title.className`, so Lumino's next tab render restores our class and `refreshAllTabColours` skips the tab (it only paints tabs with no colour class - `index.js:143-156`).

Failure scenario (FACT, traced): user hand-sets a Claude tab to `rose`, later runs `/color blue`. The tab and the row stay `rose` forever. Right-click → Clear does not restore `/color` control; nothing in the UI reveals an override exists. There is no code path that ever POSTs `colour: null`.

The new spec's third test ("the override is a preference, not a one-way door", line 96) proves this only against the raw HTTP route with an explicit `null` body - a request the shipped frontend never sends. It is a green test for a capability the product does not have.

Fix: either wire the companion's Clear (or a panel affordance) to `this._colours.set(id, null)`, or drop that spec's closing claim and state the lock-in in the docstring at `terminals.ts:309-312`. The second is the surgical option; the first is what requirement 1's "last preference" actually implies.

**4. [MINOR] Two docstrings now assert the removed behaviour** - `jupyterlab_ai_code_assistants_extension/core/colour_store.py:6-8` ("the write-back beats the default everywhere except a `native` provider, where the assistant owns its own colour") and `core/routes.py:514-516` ("whose colour store refuses every write (`ColoursHandler`)"). Both are the module- and class-level contract a maintainer reads first, and both are now false. The change updated `_effective_colour` and `ColoursHandler` prose but not these.

**5. [MINOR] `BranchHandler`'s native guard survives on a rationale that no longer exists** - `core/routes.py:549`. The guard is still correct (server-side `inherit_colour` would resolve `get_colour(parent) or default` and pin a fork to the parent's `/color` tint - the very thing `panel.ts:917-924` explains), but its stated reason at `routes.py:514-516` is the deleted 400. A maintainer who checks and finds writes now accepted will delete the guard. No native provider uses `SERVER_MINTED_FORKS` today (Claude is `native-flag`, `src/providers/claude.ts:49`), so this is latent, not live. Fix: restate the reason as "never seed a fork with the parent's assistant-chosen tint".

**6. [MINOR] Orphaned import** - `jupyterlab_ai_code_assistants_extension/tests/test_colour_store.py:14`. `import tornado` was used only by the deleted `pytest.raises(tornado.httpclient.HTTPClientError)` block; grep confirms line 14 is now its only occurrence. The change created it, so it goes with the change.

**7. [MINOR] The new early return leaves a stale applied colour on screen** - `src/core/terminals.ts:320-326`. Returning without touching the widget preserves the *record* (localStorage) but not the *display*: if an earlier pass put `jp-colourful-tab-sky` in `widget.title.className`, that class rides every Lumino re-render, and `refreshAllTabColours` will not paint the user's new menu colour over a tab that already has a colour class (`index.js:143-156`). Narrow trigger - attribution must go from resolvable to unresolvable on a terminal we already tinted - but the fix is one line and strictly better: `this._applyColour(widget, null); return;`. `setColour(widget, null)` is falsy so it does **not** call `releaseMenuColour`, the class is stripped, and the companion's own refresh paints the user's colour back.
