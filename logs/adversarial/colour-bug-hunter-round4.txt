## (b) New defects

**1. [MAJOR] The losing `_openContextMenu` closes the menu the user is looking at, re-opens it for the *other* row, and now points `Remove` at that other row** - `src/core/panel.ts:2003` (`_rebuildContextMenu`) and `:2007-2008`, with no generation guard against the awaits at `:1933` and `:1980-1988`.

Scenario. Row A is a branchy project (`extra_sessions > 0`), row B is a single-conversation row.
1. t=0 right-click A. `panel.ts:1410` sets `_activeSession = A`, `:1411` highlights A's row, `_openContextMenu(A)` awaits `_fetchBranches` at `:1933` (say 400 ms - a cold `list_branches` over a large store, or any latency).
2. t=80 ms nothing has appeared, so the user right-clicks B. `_activeSession = B`, row B highlighted. B skips the branch fetch, its `load()` returns in ~5 ms, `_resettableColours` is computed for B, `_rebuildContextMenu(false)`, `_activeSession = B`, menu **opens at B**.
3. t=400 ms A's fetch resolves. A's continuation runs `Promise.race` (`:1980`), then at `:2003` calls `_rebuildContextMenu(true)` -> `clearItems()` -> **B's visible menu is closed**, `aboutToClose` fires -> `_setActiveRow(null)` (`:1873`) clears the highlight. Then `:2007` sets `_activeSession = A` and `:2008` re-opens at A's coordinates with A's items.
4. The user is now looking at a menu that jumped position, with **no row highlighted**, whose `Remove` (`:1919`, reading `active()` at `:1618`) deletes **project A's entire history** - the row they abandoned.

The round-3 re-assert is what makes step 4 destructive: before it, `_activeSession` stayed B (the last row right-clicked and the highlighted one) and only the *items* were wrong. Fix: stamp each call and bail before it can touch shared state -
```ts
const gen = ++this._menuGeneration;   // before the first await
...
if (gen !== this._menuGeneration) { return; }  // immediately before line 2003
```
This covers both awaits, and is the only guard that keeps the visible menu, the highlight and `active()` on one row.

**2. [MAJOR] The "a file with no `overrides` is all hand-set" rule reintroduces the un-inherit bug on every existing install - and the comment justifying it is factually false** - `jupyterlab_ai_code_assistants_extension/core/colour_store.py:42-45` and its client twin `src/core/colour.ts:174-178`.

The claim is *"the only writer that predates this was the tab write-back"*. FACT, disproven from git: `inherit_colour` has written into the same `<provider>-colours.json` through `set_colour` since the shipped consolidation commit `8e62249` (`git show HEAD:...colour_store.py`, `inherit_colour` -> `set_colour` at its last line). So every pre-1.0.0 store file mixes hand-set and fork-inherited colours with no way to tell them apart, and this rule labels all of them hand-set.

TESTED (`/tmp/cr4/test_legacy_upgrade.py`, passed). Restarter journey on Kimi (`colour_source: derived`):
1. Under 0.6.17 the user colours a conversation P `mint` and branches it three times; `BranchHandler` -> `inherit_colour` writes `{"colours": {"P":"mint","C1":"mint","C2":"mint","C3":"mint"}}` - no `overrides` key.

**3. [MINOR] Two captures in flight: the later-delivered answer's `_absorb` wipes the other's colour from the cache while the server holds it** - `src/core/colour.ts:242` (`this._absorb(data)` on the POST answer), `:169-180` (`_absorb` replaces both halves wholesale).

FACT for the mechanism, TESTED in isolation against the real `ColourStore` (`/tmp/cr4/repro.js`, transpiled from `src/core/colour.ts`): two concurrent `set('A','sky')` / `set('B','mint')` with the server applying both and answering its snapshot at handling time -> in-order delivery converges to `{A,B}`; **out-of-order delivery leaves `cacheA='sky', cacheB=null, isOverride('B')=false`** while the server holds both. This is new to round 3 - before it, `set()` mutated only its own key and never took a whole-map snapshot.

Consequence for the user: terminal B was painted (so the companion already released its localStorage record), the cache no longer holds B's colour, so the next `reconcileColours` paints B with the *default* instead of the colour just picked, and `isOverride(B)` is false so **"Reset Tab Colour" omits B** - until the next `_fetch` load restores it, up to 30 s (`POLL_INTERVAL_MS`, `panel.ts:56`). Reachability rose with fix 3: every right-click now fires an extra `reconcileColours` (`panel.ts:1983`) alongside the colour loop's own.
