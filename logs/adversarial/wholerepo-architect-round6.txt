--- F1 - MINOR - two comments assert requestAPI has no timeout; DEF-72 landed
    in this same wave and made both false
    src/core/panel.ts:768, src/core/panel.ts:2393

  panel.ts:767-768, on the cleanup dialog:
    "Closing early cancels nothing (the request has no timeout either)"
  panel.ts:2393-2395, on the context-menu budget:
    "Nothing here may hold the menu hostage. `requestAPI` sets no timeout, so
     a suspended connection would otherwise cost the user Open, Copy Path and
     Remove for as long as it hangs"

  Both premises are now false: every call through requestAPI is capped at
  REQUEST_TIMEOUT_MS. Both CONCLUSIONS still hold - closing the dialog still
  cancels nothing, and 60 seconds is still far too long to hold a context menu,
  so MENU_STATE_BUDGET_MS is still justified. What is wrong is the reasoning
  record, which in this codebase is load-bearing: colour.ts:230 and
  panel.ts:1104 were both updated to cite REQUEST_TIMEOUT_MS in the same wave,
  so these two are omissions rather than a considered decision. The ledger
  itself has priced this class before - DEF-52's MAJOR text calls out that "the
  Python docstring asserted the opposite in as many words".

  Evidence: grep -rn "no timeout" src/ returns exactly these two production
  sites plus the request.spec.ts header, which is correctly past-tense.

--- F2 - MINOR - the DEF-73 re-entrancy guard freezes by hand the very list it
    could derive, which is the DEF-58 failure repeated in the same wave
    src/__tests__/colour.spec.ts:559

  The guard scans the bodies of `QUEUED = ['load', 'set', 'forget']` for calls
  back into the queue. That list is typed out. The derivable list is "methods
  whose body contains this._run(" - and it is exactly those three today, so
  deriving it costs nothing and changes no result now.

  Executed, replicating the shipped bodyOf/scan logic against colour.ts:

    methods that call _run today:          [ 'load', 'set', 'forget' ]
    injected `async prune(ids)` that wraps `await this.load()` in this._run():
    violations the shipped scan reports:   0
    injected prune body re-enters queue:   true

  So a fifth queued method that deadlocks the store is invisible to the guard,
  in both directions: it is neither scanned nor recognised as a call target.
  This is the same shape DEF-58 was raised for and fixed for, three files away,
  in the same wave - and the DEF-58 fix's own comment states the principle: "a
  guard that ages out of its own invariant".

--- F3 - MINOR - the 60s client ceiling is coupled to a Python constant by
    prose only, and the test restates the Python number as a TS literal
    src/core/request.ts:13-27, src/__tests__/request.spec.ts:101-104,
    jupyterlab_ai_code_assistants_extension/providers/codex.py:79

  request.ts derives REQUEST_TIMEOUT_MS from codex.py's _CLI_TIMEOUT_S = 30 and
  says so at length. request.spec.ts asserts the margin - but with `30_000`
  written out on the TypeScript side.

  Evidence: grep for _CLI_TIMEOUT_S across the whole repo returns codex.py:79
  (the definition), codex.py:570 (the use), and two comments. No test on either
  runtime reads it. Raise it to 90 and pytest stays green, jest stays green, and
  the client ceiling now cuts a Codex disposal on exactly the slow path the 60
  was sized for - silently, which is what the number exists to prevent.

  The repo already owns the remedy pattern: test_descriptor_parity.py exists
  because DEF-59 and DEF-60 established that a cross-runtime constant with only
  a comment binding it drifts. This one is a cross-runtime constant with only a
  comment binding it.

--- F4 - MINOR - RequestTimeoutError / isRequestTimeout are exported with zero
    production consumers
    src/core/request.ts:40, src/core/request.ts:53

  grep across src/: both names appear only in request.ts and request.spec.ts.
  The type's own docstring justifies its existence by callers needing to tell a
  slow server from a dead one - "a caller that cannot tell the two apart cannot
  report either honestly" - and cites isResponseStatus as the precedent.
  isResponseStatus has real callers (_branchByServerCopy branches on 400).
  isRequestTimeout has none.

  Mitigating: panel.ts already routes errors through three copies
  (_showError for the poll, _showActionError for a one-shot, _notifyLaunchError
  for a launch), and the timeout message is appended verbatim in each, so the
  user is not actively misled. This is dead API surface rather than a wrong
  behaviour - the fix is a consumer or a deletion, and that is a scope call for
  the owner, not something I would hold a ship on.

--- F5 - MINOR - the third copy of the recentLimit bounds lives in the schema
    GENERATOR and DEF-71 did not reach it
    scripts/generate-schema.mjs:22-37, src/core/panel.ts:90-100,
    schema/plugin.json

  DEF-71's report named three sites - index.ts, panel.ts and schema/plugin.json.
  The fix bound the first two. The third is not the emitted JSON, which is
  generated and therefore not hand-maintained; it is scripts/generate-schema.mjs,
  whose SHARED block hardcodes `default: 10, minimum: 1, maximum: 100` and
  `default: 'name'`. That file is the designated anti-drift mechanism for the
  schema, and for these four numbers it is a second source of truth against
  constants the same wave created to be the first.

  Live impact today: none - all four agree. Latent: raise the generator's
  maximum to 500 and the settings editor accepts 500 while panel.ts's clamp
  silently serves 100 rows. That is the DEF-5 class (schema and code disagreeing
  silently) that test_routes.py's schema-key test exists to prevent for key
  NAMES, applied to values.

  Direct import is not the fix - generate-schema.mjs can import lib/providers
  because those modules are plain data, but lib/core/panel.js pulls @jupyterlab
  through extensionless specifiers Node will not resolve. The cheap remedy is a
  jest assertion reading schema/plugin.json against the exported constants,
  which is the pattern colour.spec.ts and core-neutrality.spec.ts already use.
